# 开发环境指南:CLI/GUI 透明 · 容器/宿主透明 · 单内核代理栈

> 生成于 2026-09-14。适用本机(ubuntu, Supermicro X12DAi-N6, 双 RTX 4090)。

## 为什么用 tmux

**把会话从客户端剥离,只靠 CLI 就能恢复。**

| 出了什么事 | 不用 tmux | 用 tmux |
|---|---|---|
| VS Code 丢失容器连接 / 关掉编辑器 | ❌ 终端连同任务一起没 | ✅ 任务继续跑,`dtm <容器>` 原样接回 |
| SSH 断线、关掉终端窗口 | ❌ 同上 | ✅ 同上 |
| 切到 CLI 模式(`cli`)释放显存 | ❌ 桌面终端里的活全丢 | ✅ 不受影响 |
| 换个入口继续干(本地↔远程) | ❌ 只能重开、从头来 | ✅ 四个入口同一条命令接回 |

**恢复只需要 CLI** —— 不依赖 VS Code、不依赖图形界面。一条 `ssh` 加一条 `dtm` 就回到现场。

**一个例外:容器重启会丢会话。** tmux server 是容器内的进程,`docker restart` 后
`tmux ls` 报 `no server running`。但两样东西还在:

- **tmux 二进制**(overlay 层保留;容器**重建**才会丢,而启动脚本的 `ensure_tmux` 会自动装回)
- **claude 对话记录**(`~/.claude` 是宿主机 bind mount)→ 重启后 `dtm <容器>` 新建会话,
  `claude -c` 即可接续对话

所以边界是:**tmux 保护你不受"客户端消失"的影响,但保护不了"容器/主机重启"。**
长实验若怕重启,结果要落盘到挂载目录。

#### 一句话边界

**只要容器和主机不停机、你自己不 exit,tmux 会话就一直在。**

会话消失只有三种原因:

| 原因 | 说明 | 还剩什么 |
|---|---|---|
| **你自己关掉** | 窗口里敲 `exit` 把所有窗口关完,或 `tmux kill-session -t <名>` | — |
| **容器停止 / 重启** | tmux server 是容器内的进程 | tmux 二进制(overlay)、`~/.claude` 对话记录 |
| **主机重启** | 所有进程终止,`/tmp` 开机清空,socket 一并没了 | 磁盘上的一切 |

除此之外——**关编辑器、断 SSH、拔网线、RDP 掉线、`cli` 切换、换入口**——会话统统还在。

所以日常只要守住一条:**走人按 `Ctrl+b d`,不要敲 `exit`。**

### 撤销 / 恢复接口(2026-10-08 两次实测通过;第二次含 8999 规则与 claude-vpn-sync 删除后)

把这次 CCFAC 改动整体退回、或再施加,一个脚本三个子命令:

```bash
bash ~/server_config/network/scripts/netstack-ccfac-undo.sh check        # 不需要 root,只列出会动什么
sudo bash ~/server_config/network/scripts/netstack-ccfac-undo.sh undo    # 撤销
sudo bash ~/server_config/network/scripts/netstack-ccfac-undo.sh redo    # 恢复到 undo 之前(默认最新快照,可带快照目录参数)
```

| | 做什么 |
|---|---|
| undo | 快照当前版本到 `/etc/mihomo/undo-snap/ccfac-applied-<时间>/` → 退出 Clash Verge 与全部内核、清 TUN/策略规则/路由表/DNS 缓存 → 恢复 `mihomo_groups.py` `refresh.py` `ensure-campus-net.sh` `sub.url` 四个 `.bak.ccfac` → 旧 `refresh.py` 重拉订阅生成 `config.yaml` → 拉起 `mihomo.service` → 自检 |
| redo | 退 GUI 与全部内核 → 从快照复原四个文件与 `config.yaml`/known-good → 拉起 → 自检 |
| 不动 | **Beyond 的一切**(`remote-access-watchdog.sh`、计数、定时器、`/32` 路由);`netstack` 本身(旧版里 openvpn3 命令是活的、无标注);`mihomo.service` 单元文件;`openvpn.service`(保持 disabled,步骤打印"跳过(已撤销)") |

两者结束时都是**单内核 `mihomo.service` 运行、无 GUI**。各重启一次 mihomo,其 ExecStartPost 会重启一次 edge 容器,远程桌面断几十秒,watchdog 下一轮自行确认恢复。

undo 后的预期:旧订阅只有 22 个节点、`Claude` 组被旧逻辑清空填 `DIRECT`(自检显示 `Fallback → DIRECT`)、
`api.anthropic.com` 经 7897 返回 403(直连被拒);这是"初始状态"的正确样子,不是故障。

验收判据(20:53 实测值):undo → reset → redo 三次启动,`journalctl -u mihomo` 里 `Start initial configuration`
恰好 3 次,即每次启动只加载一次配置、无人热推;三次之后 8999 规则 4 条在位、edge 四条连接源地址全为 eno1、
watchdog 计数 0。非 root 跑 `netstack status` 时"9097 归属"显示 `0.0.0.0:*` 是 ss 无 root 看不到进程名所致,`sudo` 下正常。

## 一句话原则

- **`d*` 命令(宿主机)** = 从外面**进入**容器终端
- **`tmux` 命令(容器内)** = 在里面**分身 / 脱离 / 接回**会话
- 要"回来"的活用 `dtm`,不打算回来的用 `dsh`

---

## 一、终端工作流:CLI/GUI 透明,容器/宿主透明

### 命令归属:哪边有什么

| 命令 | 宿主机 | 容器内 | 说明 |
|---|:---:|:---:|---|
| `dls` `dsh` `dtm` `dtl` | ✅ | ❌ | 定义在宿主机 `~/.bashrc`,容器内刻意不定义 |
| `docker` | ✅ | ❌ | 容器没做 docker-in-docker |
| `tmux` | ❌ | ✅ | 三个开发容器均已安装 |
| `cli` `gui` `guistat` | ✅ | ❌ | 图形/CLI 模式切换 |

容器内没有 `d*` 命令是**故意的**:它们本质是 `docker exec` 的封装,人已经在容器里就不需要再"进去"一次。

---

### 宿主机命令

```bash
dls                      # 列出开发容器(自动过滤服务容器)
dtm <容器>               # 进容器 + 接上 tmux(会话名默认 work)。有则接回,无则新建
dtm <容器> <会话名>      # 指定会话名,不同任务分开
dtl <容器>               # 看该容器里有哪些 tmux 会话
dsh <容器>               # 只要一个临时 shell(退出即终止其中进程)
```

`dtm` 一步跨过边界,等价于:
```bash
docker exec -it <容器> tmux new-session -A -s work
```
所以用 `dtm` 进去后**不需要**再敲 tmux。

---

### 容器内命令(tmux 原生)

| 宿主机 | 容器内等价 |
|---|---|
| `dtm <容器>` | `tmux new-session -A -s work` |
| `dtm <容器> train` | `tmux new-session -A -s train` |
| `dtl <容器>` | `tmux ls` |
| — | `tmux attach -t <会话名>` |

#### 必记的三个快捷键

| 按键 | 作用 |
|---|---|
| `Ctrl+b` 然后 `d` | **脱离**,回宿主机,容器内进程继续跑 |
| `Ctrl+b` 然后 `c` | 新建窗口 |
| `Ctrl+b` 然后 `n` / `p` | 下一个 / 上一个窗口 |

### dsh 与 dtm 的区别

| | `dsh` | `dtm` |
|---|---|---|
| 实质 | `docker exec -it <c> bash -l` | `docker exec -it <c> tmux new-session -A -s work` |
| 断开后进程 | **随终端死**(SIGHUP) | **继续运行** |
| 能否接回界面 | ❌ | ✅ 原样回到现场 |
| 多处同时查看 | ❌ | ✅ VS Code 与 SSH 可同时 attach |
| 适合 | 几秒钟的事 | claude 会话、训练、编译 |

**`dsh` 仍有三个不可替代的场景:**
1. 要把输出留在自己终端的 scrollback 里(tmux 会接管屏幕,detach 后输出就看不到了)
2. 管道 / 重定向到宿主机:`docker exec <c> cat /workspace/out.log > ~/out.log`
3. 一次性维护动作(装包等),避免塞进 `work` 会话和 claude 混在一起

### 典型场景

#### 场景 1:随手看一眼
```bash
dsh AgentSys_dev
nvidia-smi
exit
```

#### 场景 2:跑 claude 长会话(推荐默认做法)
```bash
dtm AgentSys_dev         # 进 tmux
claude                   # 干活
# Ctrl+b 然后 d          # 脱离,claude 继续跑
# 此时可以关 SSH、关 VS Code、甚至切 CLI 模式
dtm AgentSys_dev         # 随时回来,界面一模一样
```

#### 场景 3:接管 VS Code 终端里已有的 claude
VS Code 集成终端属于客户端,CLI 下接不回。改用 tmux 重开:
```bash
dsh MLX_chipyard_dev
pkill -f claude          # 清掉旧进程,避免同会话两个进程
exit
dtm MLX_chipyard_dev     # 改用 tmux
claude -c                # ~/.claude 宿主机与容器共享,对话接得上
# Ctrl+b d 脱离
```

#### 场景 4:多任务分会话
```bash
dtm MLX_chipyard_dev train      # 训练
python train.py                 # Ctrl+b d
dtm MLX_chipyard_dev logs       # 看日志
tail -f out.log                 # Ctrl+b d
dtl MLX_chipyard_dev            # 查看:train / logs 两个会话
```

#### 场景 5:配合 CLI / GUI 切换
```bash
dtm AgentSys_dev && claude      # 把活放进 tmux,Ctrl+b d 脱离
cli                             # 切 CLI,释放约 1.3 GB 显存
dtm AgentSys_dev                # CLI 下照常接回
gui                             # 需要图形时再切回
```

### GUI / CLI 模式切换

```bash
guistat        # 当前模式 + 两卡显存 + mihomo 状态
cli            # 退到 CLI,释放显存(有确认提示)
gui            # 切回图形
cli-default    # 永久默认 CLI(重启后生效)
gui-default    # 永久默认图形
```

⚠️ `cli` 会杀掉图形会话,**先 SSH 进来再执行**(在桌面终端里跑会把自己也杀掉)。

| 切 CLI 时 | 状态 |
|---|---|
| Docker 容器(含其中的 claude / tmux) | ✅ 保留 |
| SSH | ✅ 保留 |
| mihomo(systemd 常驻) | ✅ 保留 |
| VS Code Dev Containers server(在容器内) | ✅ 保留 |
| gdm / Xorg / gnome-shell / 桌面程序 | ❌ 终止 |
| 桌面共享 3390 | ❌ 终止 |

原因:容器进程位于 `/system.slice/docker-<id>.scope`,`docker.service` 归属 `multi-user.target`,不在 `graphical.target` 的停止范围内。

### 为什么容器会话不会被杀

1. `docker.service` / `containerd.service` 的归属是 `WantedBy=multi-user.target` → `systemctl isolate multi-user.target` 时**在保留名单里**
2. `gdm.service` 的归属是 `WantedBy=graphical.target` → 只有它这类被停
3. 容器内的 vscode-server、终端、claude 的 cgroup 全是 `/system.slice/docker-<id>.scope`,由 Docker 守护进程托管,**不在图形会话进程树里**
4. `~/.claude` 是宿主机 ↔ 容器的双向 bind mount → 会话记录同源,`claude -c` / `claude --resume` 两边都能接续

**唯一会毁掉容器内一切的操作**:VS Code 的 *Rebuild Container* / *Reopen in Container*(触发容器重建)。普通的 *Attach to Running Container* 不会。


### 分流原则

规则表的**前置顺序就是优先级**:

| 优先级 | 命中对象 | 去向 | 为什么在这个位置 |
| --- | --- | --- | --- |
| 1 | `buaa.edu.cn`、四个连通性探测端点、RFC1918 三段 | `DIRECT` | 链路未认证时这些必须能直连 —— 否则连"能不能上网"都测不出来 |
| 2 | `anthropic.com` / `claude.ai` / `claude.com` / `claudeusercontent.com` / 其日志端点 / `PROCESS-PATH-REGEX,(?i)claude` | `Claude` 组 | 固定出口 IP;排在 1 之后是因为认证优先于一切 |
| 3 | 其余 2 万余条规则 | 各服务组 → `Auto` / `DIRECT` | 原有策略不变 |

- `tun.auto-route: true` 通过策略路由把普通流量交给 `Mihomo` 虚拟网卡。
- `fake-ip` 让域名规则在 TUN 层仍可匹配;需要底层直连的域名必须加入
  `dns.fake-ip-filter` 并配套前置 `DIRECT` 或主表明细路由。
- **节点自身的 server 域名必须在 `fake-ip-filter` 里**,否则 mihomo 连自己的
  节点时可能拿到 `28.x` 假地址。这一条现在由 `ensure_fakeip_filter()` 从
  `proxies` 自动派生 —— 2026-10-07 就是因为机场改了 CDN 域名、旧条目
  `*.oix_nodes.com` 变成死条目而踩过。
- Claude 规则同理由 `ensure_claude_rules()` 每天重放一次:
  2026-10-08 它们被 `remove-claude-routing.sh` 连带删掉过一次。
- Beyond 节点、校园网认证页等基础设施流量按各自章节的直连规则处理。

#### 最隐蔽的一类故障:两个内核同时在跑

2026-10-08 实测到过一次,两边**订阅还不一样**:

```
systemd mihomo.service : 持有 Mihomo TUN、rule 模式、旧订阅   ← 实际承载全局流量
Clash Verge GUI 的内核 : 无 TUN、global 模式、CCFAC 订阅
                         但占着 7897 / 7899 / 9097
```

症状极具欺骗性:**浏览器和终端都正常**(它们用 7897),`systemctl status mihomo`
也是 `active`,但任何对 `127.0.0.1:9097` 的查询问到的都是 **GUI 那个内核** ——
"查了 API,结论是好的",而系统服务其实跑着完全不同的一套。
一旦关掉 GUI 或进 CLI 模式,立刻退回旧订阅。

判据只有一条,`netstack status` 已内置:

```bash
netstack status | grep -E '内核进程|9097 归属'
#   内核进程  : 1 个 (单内核,正常)
#   9097 归属 : users:(("verge-mihomo",pid=...))    ← 该 pid 的 -d 应为 /etc/mihomo
```

判进程必须用 `pgrep -ax verge-mihomo`(精确匹配进程名)。用 `-f` 会把调用方
自己的 shell 命令行也匹配上,计数永远偏大 —— 这个坑当天也踩过一次。

#### 更隐蔽的一类:用户级残留服务往 9097 推配置(2026-10-08 晚定位)

症状:`mihomo.service` 刚起来时一切正确(`rule`、TUN 在、`Claude` 组 Fallback),
**约 9 秒后**日志再出现一次 `Start initial configuration`,之后 `mode` 变 `global`、
`Mihomo` 网卡消失、`Claude` 组变成 118 个成员的 Selector —— 而此时**没有 GUI 在跑**。

元凶是 openvpn3 时代的用户级单元 `~/.config/systemd/user/claude-vpn-sync.service`:
它监听 `ip monitor link`,找一个"不是 Mihomo 的 tun 设备"当作 OpenVPN 的 tun,
然后把 Clash Verge 的 `clash-verge.yaml` 打补丁后 `PUT /configs` 推进 `127.0.0.1:9097`。
openvpn3 撤销后,Beyond 的 `utun0` 正好满足这个判据;而 mihomo 每次启动的 ExecStartPost
都会重启 edge 容器、`utun0` 重新出现,于是**每次启动必现**。它的日志
`~/.cache/claude-vpn-sync/sync.log` 里每行 `mihomo reload HTTP 204` 都对应一次覆盖。

当天两次把这个现象归因给 Clash Verge GUI(GUI 确实也会推,但退出后仍复现才暴露了它)。

```bash
systemctl --user is-enabled claude-vpn-sync.service        # 必须是 disabled
systemctl --user disable --now claude-vpn-sync.service     # 处置(install-ccfac.sh 第 8 步也会做)
# 不重启内核、直接让它从磁盘配置重新加载:
curl -s -o /dev/null -w '%{http_code}\n' -X PUT -H 'Content-Type: application/json' \
  -d '{"path":"/etc/mihomo/config.yaml","force":true}' http://127.0.0.1:9097/configs   # 204
```

判据:`journalctl -u mihomo` 里一次启动只应有**一次** `Start initial configuration in progress`
(刷新定时器的热重载除外)。多出来的每一次都有人在推。

### 联网优先:代理必须排在"能上网"之后(2026-10-07 修)

#### 问题:顺序颠倒导致死锁

重启后 mihomo 自动起来接管全局路由,但校园网还没认证。此时:

1. 认证域名被 **fake-ip** 接管 → 浏览器拿到 `28.0.0.x` 假地址
2. 该域名**没有专属规则** → 落到 `MATCH,Others` → `Others` 指向 `Proxy` → 走代理
3. 而代理此刻**根本连不上**(没认证就没有外网)
4. → 认证页打不开 → **死锁**,人在外地完全没法恢复

正确顺序是:**先能联网 → 认证 → 才轮到代理。**

#### 处置一:新增 `ensure-campus-net.sh` 作为第一个 ExecStartPre

```
mihomo.service
 ├─ ExecStartPre ① ensure-campus-net.sh    ← 新增,永远排第一
 ├─ ExecStartPre ③ ensure-config.sh
 ├─ ExecStart       verge-mihomo
 └─ ExecStartPost …
```

它向无劫持的 204 端点探测,判三种状态并写入 `/run/campus-net-state`:

| 状态 | 判据 | 动作 |
| --- | --- | --- |
| `online` | HTTP 204 且响应体为空 | 正常走完启动链 |
| `captive` | 200/302 且响应含跳转/portal 关键字 | 应用认证页三层加固;日志明确提示去认证 |
| `offline` | 两个端点都连不上 | 日志指出是物理问题,并说明重启无效 |

**它从不阻断 mihomo 启动** —— 阻断会彻底断网,比"没有代理"更糟。

#### 处置二:认证页三层强制直连(`campus-portal-direct.py`)

你要的"最高优先级直连"做了三层,前两层保证不走代理,第三层保证**连 mihomo 都不经过**:

| 层 | 手段 | 即使…也有效 |
| --- | --- | --- |
| ① | `dns.fake-ip-filter` 加认证域名 | 浏览器拿到**真实 IP** 而非 `28.0.0.x` |
| ② | `rules` **最前面**插 `DOMAIN-SUFFIX/IP-CIDR → DIRECT` | 规则顺序匹配,插在后面会被前面两万条抢先命中 |
| ③ | `tun.route-exclude-address` 加 RFC1918 | **mihomo 配置坏了、正在重启、分组全退化** 时照样能开认证页 |

落地后 `rules` 的前 8 条就是这些直连规则(净增 7 条,原有的 `IP-CIDR,10.0.0.0/8,DIRECT` 被去重移到最前)。

第 ③ 层的安全性已逐项核对:Beyond overlay 是 `100.64.0.0/16`、mihomo 的 fake-ip 是
`28.0.0.0/8`,**都不在 RFC1918 内**,不受影响;规则里本来就有
`IP-CIDR,10.0.0.0/8,DIRECT`,语义一致,只是提前到了路由层。唯一代价是
"访问某个内网 IP 需要经代理"会失效 —— 本机无此需求。

#### 处置三:重启次数上限(`MAX_REBOOTS=3`)

原来只有"两次至少隔 2 小时"的冷却,**没有"最多 N 次"** —— 物理链路不通时会
每 2 小时重启一次、无限循环,还掩盖真因。

现在 L4 重启前有**四道闸**,全部通过才真正重启:

| 闸 | 参数 | 拦的是 |
| --- | --- | --- |
| ① | `MIN_UPTIME=900` | 开机不足 15 分钟不重启(防引导循环) |
| ② | `COOLDOWN_SEC=7200` | 两次至少隔 2 小时 |
| ③ | **链路必须 `online`** | `captive`/`offline` 时重启无用 —— 现场再探一次,不拿开机时的过期结论做决定 |
| ④ | **`MAX_REBOOTS=3`** | 连续 3 次仍不恢复就停手,记日志等人工 |

计数写在 `/var/lib/remote-access-watchdog.rebootcount`(跨重启保留),
**隧道一旦确认健康即自动归零** —— 下次真故障仍有完整 3 次机会。

逻辑仿真(物理链路断的场景):第 5/10/15 轮各重启一次,第 20 轮达上限后停手。

### 自动选优:Auto 组(2026-09-29/30 定位并修复)

#### 症状:容器"网络不通",但只是部分站点

`baidu` / 清华源 / ModelScope 正常,`huggingface.co` / `github.com` 全部
`HTTP=000`。容易误判成"容器出口只有国内白名单"或"SNI 层被掐断"。

**两个关键的误判要避开:**

| 看起来像 | 实际是 |
| --- | --- |
| `hf-mirror.com` 解析到 `28.0.0.209`,像 DNS 污染 | `28.0.0.0/8` 是 mihomo 自己的 **fake-ip 段**,这是正常行为 |
| 容器出口被限制 | 三个 dev 容器都是 **host 网络**,与主机共享 netns —— **主机上一模一样失败** |

**第一步永远是:在主机上测同样的目标。** 主机也失败就与容器无关。

#### 根因:Proxy 是 Selector,选中的节点挂了没有任何自动恢复

```
订阅 44 个节点,mihomo 标记 alive 的:1 个
当前选中节点延迟测试:Timeout
```

`Proxy` 组是 `Selector`(手动选择)且成员直接是**具体节点**。选中的那个一挂,
所有命中 `Proxy` 的规则一起断。而地区组本来就是 `fallback`(会自动切),
但 `Proxy` 的成员不是地区组,这个能力完全没被用上。

这也解释了"只有国内白名单可用":`baidu` 等命中 `Domestic → DIRECT` 不经节点;
`huggingface` / `github` 命中 `Proxy`,节点挂了就断。

#### 处置:新增 Auto(url-test)组

```yaml
- name: Auto
  type: url-test
  url: http://www.gstatic.com/generate_204
  interval: 300        # 每 5 分钟复测
  tolerance: 50        # 差值 <50ms 不切,避免反复抖动
  proxies: [ …全部订阅节点… ]
```

`Proxy` 的成员改为,并默认选 `Auto`:

```
[Auto, 香港, 日本, 美国, 新加坡, <具体节点…>, DIRECT, Direct-eno1]
```

既有自动故障转移,又保留手动固定某节点/某地区的能力。
`Proxy` 加入 `ALWAYS_REBUILD`:它是总出口,即使引用了别的组也必须每次重建,
否则每日刷新拉到的新节点永远进不去。

部署:`sudo bash network/scripts/install-auto-group.sh`(幂等,内置安全闸)。

#### 必须知道的行为:fallback 会退到 DIRECT,url-test 不会

`fallback` 的语义是"按成员顺序取第一个可用的"。地区组的成员末尾有 `DIRECT` 兜底,
所以**该地区节点全挂时会退到 DIRECT —— 即直连、不走代理**:

```
香港     now=香港 01 - 1倍率      节点 8 个,alive 7 个
日本     now=DIRECT             节点 8 个,alive 0 个   ← 退化成直连了
```

不报错,但也没有代理效果。**想确保一定走代理就选 `Auto`** —— 它的成员**只含真实
订阅节点,不含 `DIRECT` 也不含本地伪出口**,所以不会静默退化成直连。

#### 一个会让整份配置失效的 bug:地区正则缺词边界

```python
re.search("US", "DisneyPlus", re.I)   # → 命中 "Plus" 里的 "us"
```

`DisneyPlus` 被误判成美国地区组、被塞进 `Proxy` 成员,而它自己又引用 `Proxy`:

```
level=error msg="loop is detected in ProxyGroup, please check following ProxyGroups: [Proxy DisneyPlus]"
configuration file test failed
```

修复两道:所有英文缩写加 `\b`(`\bUSA?\b`、`\bHK\b` …);另加**结构性保险** ——

### 已知 Bug 记录(2026-09-25 定位并修复):分组退化导致静默直连

**现象**:`github.com` 连不上,而 `api.github.com` 正常。

**根因**:`Proxy` 组和四个地区组的成员**只剩 `DIRECT` 一个**。规则
`DOMAIN-KEYWORD,github,Proxy` 把流量送进 `Proxy` 组,该组选 `DIRECT` → 实际直连 →
不通。`api.github.com` 另有一条 `DOMAIN,api.github.com,OpenAI`,而 `OpenAI` 组引用
`Proxy`/地区组之外还有自己的成员,所以反而正常。

诊断关键是 `/connections` API 里的 chain 字段:

```bash
curl -s http://127.0.0.1:9097/connections | python3 -c '
import sys,json
for c in json.load(sys.stdin)["connections"]:
    print(c["metadata"].get("host"), "→", " → ".join(c["chains"][::-1]))'
```

坏的时候输出 `github.com → Proxy → DIRECT`,好的时候是
`github.com → Proxy → 香港 Premium 02 - 1倍率`。

**为什么会退化**:`refresh.py` 的 `prune` 与 `prune-dangling-proxies.py`
**只做减法**。机场改名后旧引用悬空被剔除,组被填 `["DIRECT"]` 占位,而
**没有任何环节把新节点填回去**。42 个节点全部存活,只是没挂进组里。
本机从 2026-09-14 的备份起就是这个状态。

**更糟的一环**:`ensure-config.sh` 原来只要配置"能解析"就存 known-good 快照。
而退化配置完全能解析 —— 于是坏状态被固化进 `config.good.yaml`,**连回滚都救不回来**。

**处置**:新增共享模块 `mihomo_groups.py`,两个功能:

| 函数 | 作用 |
| --- | --- |
| `rebuild(cfg)` | 重建聚合型组成员。`Claude` = 名字同时含「美国」「小水管」「固定IP」的节点(fallback);`Auto` = 倍率 ≤ `AUTO_MAX_RATE` 的全部节点(url-test);`Proxy` = `[Auto, Claude] + 全部节点 + DIRECT`;其余服务组一律 `[Auto, Proxy, DIRECT]`。只认关键词,不认编号 / 机房代号 / 倍率后缀 |
| `group_health(cfg)` | 检测聚合型组是否退化成只剩 `DIRECT`,返回退化的组名 |

接入三处:

- `refresh.py`:`prune` 之后调 `rebuild`;校验通过后再过一道 `group_health` 门禁,退化则**放弃刷新**而不是落地
- `prune-dangling-proxies.py`:剔除后补一次 `rebuild`
- `ensure-config.sh`:存 known-good 快照**之前**过 `group_health`;退化则只放行、不更新快照,并提示跑一次 refresh

重建逻辑刻意保守:**引用了其它组的组一律不动**(如 `OpenAI: [Proxy, 香港, …]`),
它们靠被引用的组自动获得节点;`AdBlock` 在 `SKIP_GROUPS` 里跳过。

**验证**(以 2026-09-25 那份退化备份为输入):

| 组 | 修前 | 修后 |
| --- | --- | --- |
| Proxy | 1 (`DIRECT`) | 45 |
| 香港 | 1 | 8 |
| 日本 | 1 | 9 |
| 美国 | 1 | 15 |
| 新加坡 | 1 | 9 |

`group_health` 判定由"5 个组退化"变为"无退化",`verge-mihomo -t` 校验通过。
门禁三场景:退化配置→修好后放行;人为清空 `Proxy`→拦住;订阅节点为 0→不误报。

**部署**:`sudo bash network/scripts/install-group-rebuild.sh`(幂等)。

**残留边界**:
- `Auto` 只收倍率 ≤ `AUTO_MAX_RATE`(当前 1.5)的节点。url-test 按延迟选,
  而"顶级 / 小水管"这类高倍率节点延迟通常最低、会被优先选中 —— 放进去等于
  让日常流量持续烧高倍率额度。它们仍可在 `Proxy` 里手动选。
- `Claude` 组若一个节点都匹配不到,`rebuild()` 会打一行告警并临时退回
  `[Auto, Proxy]`。此时 Claude 的出口 IP 不再固定,需人工处理
  (换订阅,或改 `CLAUDE_KEYS`)。

### Obsidian MCP:离线可用与 CLI 模式

Obsidian 的 Local REST API(`127.0.0.1:27123`)是 `obsidian` MCP 的后端。两件事容易踩:

#### ① Obsidian 本体:已做成 systemd 用户服务,CLI 模式下照常运行

```
obsidian.service (user)
  Description=Obsidian (Local REST API for the obsidian MCP)
              - always on, window when a GUI session exists, headless otherwise
  ExecStart=%h/.local/bin/obsidian-managed
  WantedBy=default.target          active / enabled
```

**所以 `cli` 切到命令行模式不会让 27123 断掉** —— 它会转为 headless 继续跑。
有图形会话时才显示窗口。这一点与「什么能活过什么」那张表一致。

排查:`systemctl --user status obsidian` + `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:27123/`(期望 200)。

#### ② MCP 服务端:必须固定版本,否则每次启动都要联网

**症状**:`obsidian (CONNECTION_CLOSED): Connection closed`,时好时坏 ——
网络正常时能连、网络一抖就断,而 27123 本身始终是好的。

**根因**:`~/.claude.json` 里 `mcpServers.obsidian.args` 若写 `obsidian-mcp-server@latest`,
`bunx` **每次启动都要联网解析版本**。网络栈抖动(如 mihomo 重启、Beyond 重连)即失败。

**修复**:改为固定版本,走 `~/.bun/install/cache/` 里已有的副本:

```jsonc
// ~/.claude.json
"mcpServers": { "obsidian": {
    "type": "stdio",
    "command": "/home/descfly/.bun/bin/bunx",
    "args": ["obsidian-mcp-server@3.5.4"]   // ← 不要用 @latest
    // env 含 OBSIDIAN_API_KEY,该文件不入库
}}
```

查可用版本:`ls -d ~/.bun/install/cache/obsidian-mcp-server@* | sed 's|.*/||'`
升级时手动改版本号,并确认缓存里有对应副本。

#### ③ 容器:已有私有垫片,无需改动

三个开发容器的 `~/.bun/bin/bunx` 是**容器私有的 bash 垫片**,按 glob 拦截
`obsidian-mcp-server*`(**版本号无关**,`@latest` 与 `@3.5.4` 同样命中),
直接 exec 预装副本 `~/.bun/obsidian-mcp-server/node_modules/.../dist/index.js`,
**完全离线**。所以容器侧不需要跟着改。

> 容器里的 `.claude.json` 与宿主机**不是同一个文件**:虽然声明了 bind mount,
> 但 Claude Code 会原子替换该文件,mount 随即断开,各自独立(inode 不同)。
> 改宿主机不会传导到容器 —— 好在容器有垫片,本来就不受影响。

#### 生效粒度

**只需重启 claude 会话,不必重启容器或主机。** MCP 服务端是 Claude Code
每次启动时 spawn 的子进程,读取当时的 `~/.claude.json`。

### 常见异常与处置

| 现象 | 原因 | 处置 |
|---|---|---|
| Obsidian MCP 时断时续(CONNECTION_CLOSED) | `args` 用了 `@latest`,每次启动要联网解析 | 改为固定版本,见「Obsidian MCP」一节;27123 本身通常是好的 |
| Beyond 隧道断、远程连不上 | `/32` 路由丢失导致底层流量进入 TUN | 先 `sudo /etc/mihomo/ensure-beyond-underlay.sh` 重装路由,再 `docker restart beyondnetwork_edge`;判据见「Beyond 底层出口 → 验证成功的标志」 |
| `netstack status` 显示 `Claude 出口: Selector → 默认节点`、`Mihomo TUN: 未出现`,但 `mihomo` 是 active 且配置校验通过 | 有东西通过 9097 往内核推了 GUI 的 profile:Clash Verge 开着,或用户级 `claude-vpn-sync.service` 仍 enabled | 退出 GUI;`systemctl --user disable --now claude-vpn-sync.service`;然后 `sudo netstack heal` 或对 9097 `PUT /configs` 重载磁盘配置 |

⚠️ **不要打开 Clash Verge GUI** —— 它会另起一个内核,与 `mihomo.service` 抢 `Mihomo` TUN 和 7897 端口。

### 远程 SSH 免密登录:公钥双端配置

远程地址是 `192.168.31.116`(经 Beyond overlay 到达,客户端源地址形如 `100.64.0.x`)。

**当前状态(2026-09-25 实测)**:主机侧公钥认证**本来就是开着的**
(`PubkeyAuthentication` 取默认 `yes`),`~/.ssh/authorized_keys` 里已有 3 把公钥,
权限也正确(`authorized_keys` 600、`~/.ssh` 700)。但日志显示所有登录都是
`Accepted password`,且本次启动**没有任何公钥尝试记录** —— 说明
**客户端根本没提供公钥**,不是主机侧拒绝。所以要配的主要是客户端。

```bash
# 主机侧自检:确认公钥认证已启用、密钥已就位
sshd -T 2>/dev/null | grep -E '^(pubkeyauthentication|passwordauthentication|authorizedkeysfile)'
grep -cE '^(ssh-rsa|ssh-ed25519|ecdsa-)' ~/.ssh/authorized_keys     # 有效公钥条数
stat -c '%a %n' ~/.ssh ~/.ssh/authorized_keys                        # 必须是 700 和 600
```

#### 主机换 IP 后公钥"失效"(2026-09-25 实际发生)

**症状**:原本公钥免密好用,主机 IP 从 `192.168.10.86` 换到 `192.168.31.116` 后变成要输密码。

**这不是公钥失效**。`authorized_keys` 与主机 IP 无关,实测确认:

```
# 换 IP 前成功的登录,用的就是现在仍在 authorized_keys 里的那把
Accepted publickey for descfly from 100.64.0.12 ssh2: RSA SHA256:1V4REVWTNy8nlsYWXQrGYpvjnXefgth3NDDBnYGl0nM
                                                           ↑ 匹配 rog@DESKTOP-SAP1K0S (RSA 3072)
```

且三把公钥都**没有** `from=` 之类的 IP 限制,host key 自 2024-06-14 未更换。

**真正原因**:客户端 `~/.ssh/config` 里的 `Host` 块绑着旧 IP：

```
Host 192.168.10.86
    IdentityFile ~/.ssh/id_rsa_xxx
```

连新 IP 时这个块**匹配不上** → 没有指定 `IdentityFile` → ssh 只试默认文件名
(`id_rsa` / `id_ed25519`)→ 非默认名的私钥不会被提供 → 回落到密码认证。
主机侧日志的特征是:**完全没有公钥尝试记录**,直接 `Accepted password`。

**改法**:客户端的 `Host` 块同时覆盖新 IP 与别名,`IdentityFile` 保持原样。

```
Host buaa 192.168.31.116
    HostName 192.168.31.116
    User descfly
    IdentityFile ~/.ssh/id_rsa_buaa
    IdentitiesOnly yes
```

不确定私钥文件名时,用指纹反查(主机侧 `ssh-keygen -lf` 每把公钥即可拿到指纹):

```bash
# Linux / macOS
for k in ~/.ssh/id_*; do case "$k" in *.pub) ;; *) ssh-keygen -lf "$k" 2>/dev/null;; esac; done

# Windows PowerShell
Get-ChildItem $env:USERPROFILE\.ssh\* -Exclude *.pub,config,known_hosts* |
  ForEach-Object { ssh-keygen -lf $_.FullName }
```

**`known_hosts` 会提示一次**:新 IP 是新条目,首次连接要求确认指纹 —— 正常现象,
不是中间人。本机 host key 指纹(与 IP 无关,可长期对照):

| 类型 | 指纹 |
| --- | --- |
| ED25519 | `SHA256:aN9mlSHSJqNp46Bf3znjGYtmV4aQemxffGD+suVBx9Y` |
| RSA | `SHA256:XN2Z+owBaskRWcY+NESAmlOCFAU+Giz7xoiCBB7GP+Q` |
| ECDSA | `SHA256:eWKR6njSDNWtc1RCNek6wn2PVT1DGxYYYnkg63U1N0Y` |

旧 IP 的 `known_hosts` 条目可以留着(将来回切 eno2 仍可用);要清则
`ssh-keygen -R 192.168.10.86`。

**验证**:客户端 `ssh -v buaa 2>&1 | grep -iE 'Offering|Authenticated'`,
看到 `Authenticated to ... using "publickey"` 即成功;主机侧
`journalctl -u ssh --since -10min | grep Accepted` 应显示 `publickey` 而非 `password`。

**排查顺序的教训**:主机 IP 变更后出现"要输密码",**先查客户端 config 的 Host 块**,
不要急着重新生成密钥或重复 `ssh-copy-id` —— 后者会在 `authorized_keys` 里堆重复条目。

#### 客户端:生成密钥并装到主机

**Linux / macOS**

```bash
# ① 生成密钥对。优先 ed25519(更短更快);只有对端老旧才用 RSA
ssh-keygen -t ed25519 -C "$(whoami)@$(hostname)-to-buaa-host"
#   需要 RSA 时:ssh-keygen -t rsa -b 4096 -C "..."
#   一路回车即可;passphrase 建议设,配合 ssh-agent 不影响免密体验

# ② 把公钥装到主机(这一步仍需输一次密码,之后就不用了)
ssh-copy-id -i ~/.ssh/id_ed25519.pub descfly@192.168.31.116

# ③ 测试
ssh -o PreferredAuthentications=publickey descfly@192.168.31.116 'echo OK; id -un'
```

**Windows(PowerShell,含 ROG 那台)**

```powershell
ssh-keygen -t ed25519 -C "$env:USERNAME@$env:COMPUTERNAME-to-buaa-host"
# Windows 没有 ssh-copy-id,手工追加:
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh descfly@192.168.31.116 "cat >> ~/.ssh/authorized_keys"
ssh -o PreferredAuthentications=publickey descfly@192.168.31.116 "echo OK"
```

`ssh-copy-id` 不可用时的通用做法(任何平台都适用):

```bash
ssh descfly@192.168.31.116 "umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys" < ~/.ssh/id_ed25519.pub
```

> 注意是 `>>` **追加**,不是 `>` 覆盖 —— 主机上已有 3 把别的机器的公钥,覆盖会把它们清掉。

#### 客户端:写进 `~/.ssh/config`,以后只敲一个别名

```
Host buaa
    HostName 192.168.31.116
    User descfly
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    # overlay 链路偶有抖动,保活避免会话被判超时
    ServerAliveInterval 30
    ServerAliveCountMax 6
    TCPKeepAlive yes
    # 复用连接,后续 ssh/scp 秒开
    ControlMaster auto
    ControlPath ~/.ssh/cm-%r@%h:%p
    ControlPersist 10m
    Compression yes
```

之后 `ssh buaa` 即可;`scp file buaa:~/` 也走同一条复用连接。

`IdentitiesOnly yes` 很关键:客户端若有多把密钥,ssh 会逐个试,
可能在试到正确那把之前就撞上 `MaxAuthTries` 被拒。

#### 主机侧:可选的收尾

```bash
# 清掉 authorized_keys 末尾的空行(无害,只是整洁)
sed -i '/^[[:space:]]*$/d' ~/.ssh/authorized_keys

# 给每把公钥加备注,便于日后识别与吊销(第三列就是备注)
awk '{print $3}' ~/.ssh/authorized_keys
```

**关闭密码登录 —— 确认公钥能用之后再做,否则会把自己锁在外面。**

```bash
# 前置条件:另开一个终端,已用公钥成功登录并保持连接不断
sudo tee /etc/ssh/sshd_config.d/99-no-password.conf <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF
sudo sshd -t && sudo systemctl restart ssh.socket ssh.service
```

`sudo sshd -t` 是语法校验,**不通过就不要重启**。本机 SSH 是 socket 激活
(`ssh.socket` enabled + active,`ssh.service` 显示 `disabled` 属正常),
所以两个都要重启。

### Beyond 底层出口:必须绕开 mihomo TUN(2026-09-20 定位,2026-09-25 迁到 eno1)

**这是本机最容易搞错的一处,先把结论说清楚:**

> Beyond 的底层流量必须**在路由层**就从指定网卡直出,**不能进 Mihomo TUN**。
> 让它「进 TUN 之后再绑网卡出站」是无效的 —— 两者机制不同,结果也不同。
>
> **当前出口网卡是 `eno1`**(2026-09-25 从 eno2 迁移,原因见本节末「为什么离开 eno2」)。
> 出口网卡写在 `/etc/mihomo/beyond.conf` 的 `BEYOND_IFACE` 一行,源地址、网关、
> 是否需要 `onlink` 全部自动推导 —— 换网卡不必改代码。

#### 为什么

NAT 穿透要求 edge 的 UDP **源端口映射稳定**。若流量进了 Mihomo TUN,
mihomo 会**终结这条 UDP 再以自己的端口重新发起**:

- 出站正常 → edge 能注册、能收到 Beyond 的保活包
- 入站打洞失败 → 对端按 Beyond 记录的地址打过来,打到的是 mihomo 的临时映射
- 表现:`utun0` 有少量 `rx`(保活),**`tx` 恒为 0**,远端怎么都连不上

#### 正确做法:主表 `/32` 明细路由 + `onlink`

mihomo 的规则链是:

```
9002: lookup 2022 suppress_prefixlength 0   → 表 2022 只有 default dev Mihomo,被 suppress 跳过
9003: lookup main suppress_prefixlength 0   → 查主表的【明细】路由  ← 在这里拦截
```

所以在**主表**给 Beyond 节点装 `/32` 路由,规则 9003 就会命中它,流量**根本不进 TUN**:

```bash
# 网关/网卡/是否需要 onlink 由脚本自动推导,下面是 eno1 的实际形态:
ip route replace <节点IP>/32 via 192.168.31.1 dev eno1
```

由 `/etc/mihomo/ensure-beyond-underlay.sh` 自动完成,已接入启动链(见「启动链」一节第 ⑤ 步)。
出口网卡读 `/etc/mihomo/beyond.conf` 的 `BEYOND_IFACE`(当前 `eno1`)。

#### 脚本自身的两个失效模式(2026-09-25 自审时修复)

**① 网卡"存在"不等于"可用"。** 拔掉网线后 `ip link show` 仍然成功(link 还在,只是
`operstate=down`、`carrier=0`)。旧版只查存在性,于是会继续往一条死链路装路由。
现在同时检查 `operstate` 与 `carrier`,任一不满足就**保留现有路由原样退出**。

**② 必须「先装后剪」,不能「先删后装」。** 旧版先按上次的清单 `ip route del`,
再装新的。一旦装不上(网卡 down、网关不可达、无 root),主表就**一条 `/32` 都没有**:

```
# 主表无 /32 时的实际走向(实测)
1.2.3.4 dev Mihomo table 2022 src 28.0.0.1     ← 进 mihomo TUN
```

这会让 mihomo 终结并重发 UDP → NAT 映射不稳定 → 隧道断。
现在的顺序是:先 `ip route replace`(幂等)装全部新路由 → **一条都没成功就直接退出、
不做任何删除** → 成功后只剪掉不在新集合里的旧条目。

验证(以 `BEYOND_IFACE` 指向一块 down 的网卡):

```
[ensure-beyond-underlay] ✗ 网卡 docker0 不可用(operstate=down carrier=0)→ 保留现有路由不动
```

以非 root 运行(装不上路由)时:

```
[ensure-beyond-underlay] ✗ 一条路由都没装上(4 次失败)→ 保留现有路由不动,不做任何删除
```

两种情况下 `/run/beyond-underlay.routes` 都**保持原内容**,不会被清空。

#### Beyond 走 eno1 时是否会被 mihomo 截走(实测:不会)

这是换到 eno1 后最该验证的一点。
结论是不会,因为拦截机制**基于路由表而非网卡**:主表的 `/32` 被规则 9003 命中,
流量在进入任何 TUN 之前就已定向。实测证据:

```bash
# ① 四条 /32 的出口与源地址
ip route get 47.94.106.154
#   → via 192.168.31.1 dev eno1 src 192.168.31.116

# ② edge 的实际会话源地址:是 eno1 的地址,不是 mihomo 的 28.0.0.1
docker exec beyondnetwork_edge ss -tunap | grep -E ':3005|:30004'
#   → 192.168.31.116:53856 → 42.240.157.83:3005

# ③ mihomo 没看到 edge 的流量
journalctl -u mihomo --since -5min | grep -c '(edge'        # → 0

```

**唯一的真实风险是 `/32` 缺失**:届时流量会落到 `dev Mihomo`,由 mihomo 中转后改变 NAT 映射。
上面的「先装后剪」就是为了保证 `/32` 永远不会因为一次失败的刷新而消失。

#### 两个必须处理的坑

| 坑 | 症状 | 处理 |
|---|---|---|
| **网关在主表里不可达** | `ip route replace ... via <网关> dev <网卡>` 报错,一条都装不上 | eno2 的直连路由被 NetworkManager 放进了**表 200**(见「回包路径」一节),主表没有,内核判定网关不可达 —— 这种情况必须加 **`onlink`**。eno1 的直连路由在主表,不需要。脚本会自动判断 |
| **DNS 解析拿到 fake-ip** | 脚本解析出 `28.0.0.x` 并据此装路由,完全无效 | `dig @223.5.5.5` 仍会被 mihomo 的 `dns-hijack any:53` 截走。必须**绑定该网卡源地址查询**:`dig -b <网卡地址> @223.5.5.5 …`(脚本自动推导);另加 `grep -v '^28\.'` 兜底 |

#### 还要把 Beyond 域名排除出 fake-ip

`/32` 路由只对**真实 IP** 生效。edge 若解析 `api1.beyondnetwork.cn` 得到 fake-ip `28.0.0.x`,
拿着假 IP 去连,路由匹配不上,控制面仍会被 mihomo 中转。所以:

```yaml
dns:
  fake-ip-filter:
    - '+.beyondnetwork.cn'
    - '+.beyondtunnel.com'
    - '+.ipw.cn'          # edge 的 IPv6 探测域名,否则日志刷 dns resolve failed
```

这样可确保 Beyond 控制面拿到真实 IP,让主表 `/32` 路由能够命中。

#### 验证成功的标志

```bash
# ① 四条路由都指向 eno2,而非 dev Mihomo
for ip in <节点IP列表>; do ip route get $ip | head -1; done
#   期望: <ip> via <该网卡网关> dev <BEYOND_IFACE>(当前 eno1 / 192.168.31.1)

# ② edge 的 UDP 会话源地址是该网卡的地址(当前 192.168.31.116),不是 28.0.0.1
docker exec beyondnetwork_edge ss -unap | grep edge
#   期望: ESTAB <本机该网卡地址>:xxxxx → <节点IP>:3005 users:(("edge",...))

# ③ mihomo 日志里不再出现 (edge) 的流量
journalctl -u mihomo --since -2min | grep -c "(edge)"
#   期望: 0(控制面与数据面都已绕开)

# ④ utun0 的 tx 开始增长(有真实对端流量,而非只有保活)
```

#### 已证伪的两种做法(勿再尝试)

| 做法 | 为什么无效 |
|---|---|
| mihomo 规则指向 `type: direct` + `interface-name: eno2` 的伪出口 | **仍先进 TUN**(源变成 `28.0.0.1`),只是出站那一跳绑了 eno2,NAT 映射依旧不稳定 |
| 只用 `tun.route-exclude-address` 排除节点 | 方向对,但排除后走**主表默认路由(eno1)**,没解决"从哪块网卡出"。`/32 + onlink` 一步同时解决两件事 |

脚本留在 `network/scripts/deprecated/` 仅作记录。

#### 为什么离开 eno2(2026-09-25,排查耗时最长的一次)

**症状**:Beyond 控制台显示 edge 离线,远端 SSH/RDP 全部不通;但主机侧所有常规检查都"正常"
—— 四条 `/32` 路由指向 eno2、edge 的 UDP 源地址是 `192.168.10.86`、mihomo 日志里 0 条 `(edge)`、
eno2 能 ping 通网关、TCP 443 能连上。重装容器、在控制台新建节点换 `EDGE_KEY`,都无效。

**根因**:**eno2 所在网段(192.168.10.x)是校园网,认证已过期。** 上游用自签证书
**透明劫持 HTTPS**,对任何请求都返回认证跳转页:

```html
<script>location.href="https://gw.buaa.edu.cn/index_67.html"</script>
Authentication is required. Click here to open the authentication page.
```

edge 期望 JSON,拿到 HTML,于是每 10 秒报一次:

```
[E] [confagent.go:87] invalid character '<' looking for beginning of value
```

永远拿不到节点列表 → `Racer` 阻塞在 `chan receive` → 隧道从未建立。

**这个故障为什么难查**:劫持发生在**应用层**,所有网络层检查都通过。

| 看起来正常的现象 | 实际情况 |
| --- | --- |
| `TCP 443 / 3005 连得上` | 连上的是**认证网关**,不是目标主机 |
| `curl` 拿到 HTTP 200 | 200 的内容是认证跳转 HTML |
| 能取到"公网 IP" | 那是认证网关回的 |
| TCP 30004 时通时不通 | 网关对不同端口的劫持行为不一致 |

**唯一可靠的判据**:`docker exec beyondnetwork_edge cat /var/log/edge.log`
—— 注意是容器内的这个文件,**不是 `docker logs`**(后者只有 `ipw.cn` 的噪音)。
以及 `curl --noproxy '*' -m 10 https://api1.beyondnetwork.cn/api/v1/smartwan/open/edge/get_nodes`:
正常应返回 **HTTP 400 且证书 `CN=*.beyondnetwork.cn`**;若返回 HTML 或
`SSL certificate problem: self-signed certificate`,就是被劫持了。

**处置**:改走 eno1(192.168.31.x),证书正常,隧道立即恢复(`utun0` rx/tx 由 `0/0` 变为持续增长,
远端 SSH 从 `100.64.0.11` 连入 `192.168.31.116:22`)。

**顺带的教训**:判断"网络通不通"时,`curl --interface eno2` 这种 `SO_BINDTODEVICE`
的测法在本机**不可靠** —— 这台机器按**源地址**分流(规则 199/200 `from 192.168.10.0/24`),
必须用 `curl --interface 192.168.10.86` 绑源 IP 才测得准。我一度因此误判"TCP 30004 被封"。

#### 为什么进一步**禁用** eno2(而不只是不用它)

只把 Beyond 挪走还不够 —— eno2 只要还在连接,就有若干条路径能把故障扩散到全机:

| 路径 | 后果 |
| --- | --- |
| 表 200 里有一条 DHCP 默认路由(metric 20500) | 任何绑定 `192.168.10.86` 作源地址的进程都会走进被劫持的链路 |
| 优先级 199/200 策略规则常驻 | `from 192.168.10.0/24` 的流量绕过主表判断 |
| eno2 的 DHCP 下发 DNS `192.168.10.1` | 一旦被 systemd-resolved 采用,**全机 DNS 都可能被校园网劫持** |
| 隧道起来时曾出现 `192.168.10.0/24 dev utun0` 进主表 | 与 eno2 自己的 LAN 路由冲突,`192.168.10.1` 被导进隧道 |

而这条链路**在结构上不可能成为备份**:门户接口显示该账号
**只允许一个设备在线**(`online_device_total: 1`),而这个位子被**上游的小米路由器
WAN**(`10.134.138.11`,被登记成一台 Windows 10)占着。eno2 直连校园网就是"第二个
设备",会话建不起来 → 被劫持。

> **更正(2026-09-25)**:早先此处写"该账号处于免费区域、没有外网额度,重新认证也无用",
> 这个推断**是错的**。路由器用的是同一个账号而 eno1 明明能上外网,`billing_name:
> 免费区域` 只是计费分区名,不代表没有外网。真实原因是唯一的设备位被路由器占着 ——
> 给 eno2 认证成功只会把路由器顶下线,连带干掉 eno1 和整个 LAN。

**处置**:`sudo bash network/scripts/disable-eno2.sh` —— 只设 `autoconnect=no` 并
`down` 掉连接,**保留连接配置**,一条命令即可回切。脚本末尾打印回切步骤(含校园网认证)。

#### eno1 的"免登录"是谁替它登录的(2026-09-25 查明)

从主机看 eno1 确实免登录(`http://connectivitycheck.gstatic.com/generate_204` 直接
返回 204,不经任何认证)。但认证是存在的,只是在**上游一跳**:

```
eno1 (192.168.31.116) → 小米路由器 (192.168.31.1) → 10.134.138.1 (校园网关)
```

经 eno1 查门户拿到的会话:

```
online_ip           10.134.138.11        ← 小米路由器的 WAN
user_name           p01442
user_mac            50-88-11-55-76-4D
online_device_total 1                     ← 只有一个设备位
在线设备明细        {"class_name":"Windows","os_name":"Windows 10","ip":"10.134.138.11"}
```

**路由器 WAN 持有那个 srun 会话**,所以 LAN 内的主机不需要认证。

**推论(直接影响冗余设计)**:

1. 路由器的会话一掉(空闲超时、被别的设备顶掉、路由器重启),**eno1 一起失去外网**,
   而主机**无法替它重新认证** —— 会话绑在路由器 WAN 的 IP/MAC 上。
2. **eno2 作为备份在结构上不可能成立**:账号只有一个设备位,被路由器占着。
   给 eno2 认证成功只会把路由器顶下线,连带干掉 eno1 和整个 LAN。
3. **这台机器目前没有可用的冗余方案** —— 两条路都依赖同一个校园账号的唯一设备位。
   真冗余只能加**独立上游**(4G/5G 随身 WiFi、手机热点)。届时改
   `/etc/mihomo/beyond.conf` 的 `BEYOND_IFACE` 一行即可切过去。

#### 需要用校园网时怎么认证(已验证可行)

然后浏览器打开 `https://gw.buaa.edu.cn/` 即可看到真实登录页
(`/srun_portal_pc?ac_id=67&theme=buaa`,srun 门户,有账号/密码/验证码)。
有验证码,所以**没有可靠的 CLI 自动登录方式**,只能在浏览器里完成。

```bash
# billing_name / user_balance / remain_bytes / online_device_total 是关键字段
```


#### 2026-10-08:`route-exclude-address` 让 `/32` 机制整体失效(已修)

`/32 + suppress_prefixlength 0` 的前提是表 2022 里**只有一条 `default dev Mihomo`**。
2026-10-07 `campus-portal-direct.py` 给 `tun.route-exclude-address` 加了 RFC1918 三段,
mihomo 从此把默认路由拆成 30 多段明细前缀(`0.0.0.0/5`、`128.0.0.0/3` …)写进表 2022;
规则 9002 的 `suppress_prefixlength 0` 只压得住前缀长度为 0 的默认路由,压不住这些拆分段,
于是节点流量在轮到主表 `/32` 之前就被送进了 TUN:

```bash
ip route get 139.196.45.11
#   139.196.45.11 dev Mihomo table 2022 src 28.0.0.1      ← 错,应为 via 192.168.31.1 dev eno1
docker exec beyondnetwork_edge ss -tnap | grep 30004
#   ESTAB 28.0.0.1:53864 139.196.45.11:30004 users:(("edge",...))   ← 源地址是 TUN 的
journalctl -u mihomo | grep '(edge)'
#   [TCP] 28.0.0.1:49292(edge) --> 47.94.106.154:30004 ... using Domestic[DIRECT]
```

白天没暴露,是因为 `claude-vpn-sync` 一直把 GUI 的无 TUN 配置推进内核;TUN 一回来,
watchdog 连续两轮判"edge 持续报错"并重启容器,再三轮就会重启主机。

**修法在路由层**:`ensure-beyond-underlay.sh` 装完 `/32` 后再装
`ip rule add to <节点>/32 lookup main priority 8999`,排在 9002 之前直接查主表;
节点 IP 随脚本变,`netstack stop` / `net-reset` 清理时连 8999 一起删。
不用 `route-exclude-address` 加节点 IP 的做法 —— mihomo 的 `PATCH /configs` 对它不生效,
只能整份配置热重载,而且静态列表跟不上节点变化。

当晚的应急:把加了节点 `/32` 的配置副本 `PUT /configs?force` 进内核,`ip route get` 立刻回到 eno1,
`docker restart beyondnetwork_edge` 后四条控制面连接源地址全部是 `192.168.31.116`。
这是内存态,**04:30 刷新会覆盖**,所以 8999 规则必须在此之前装好。

### 回包路径:非对称路由(最隐蔽的坑)

> **时效说明(2026-09-25):eno2 已禁用,本节仅作原理记录与回切依据。**
>
> 本节描述的是远程访问走 eno2 的时期。现在全机只依赖 `eno1`:`eno1` 的默认路由本就在
> 主表,不存在非对称路由问题,优先级 199/200 这两条规则**不再参与任何链路**。
> eno2 的 NetworkManager 连接已设 `autoconnect=no` 并断开,但**连接配置本身保留**
> (含 `ipv4.route-table 200` 与 `ipv4.routing-rules`),连接 down 后这两条规则自动移除,
> 需要时一条命令即可回切 —— 见下面「为什么禁用 eno2」。


**症状**:远端 TCP 握手成功,但 RDP/SSH 认证总是超时。看起来像密码问题,其实是网络。

**根因**:双网卡各有一条 DHCP 默认路由。请求从 `eno2`(192.168.10.86)进来,
回包却按主表默认路由从 `eno1`(192.168.31.x)出去,对端收不到应答。

**修复**(写进 NetworkManager,重启后持久):

```bash
nmcli con mod "<eno2 连接名>" ipv4.route-table 200
nmcli con mod "<eno2 连接名>" ipv4.routing-rules \
  "priority 199 from 192.168.10.0/24 table 254 suppress_prefixlength 0, \
   priority 200 from 192.168.10.0/24 table 200"
nmcli con up "<eno2 连接名>"
```

| 规则 | 作用 |
|---|---|
| `route-table 200` | eno2 的路由(含默认路由)放进独立表,不与 eno1 在主表争 |
| 优先级 **199** | 源自 10.x 的包**先查主表明细路由**(如 `100.64.0.0/16 → utun0`),但忽略主表默认路由 —— 少了这条,回 overlay 对端的包会被错误地送出 eno2 |
| 优先级 **200** | 其余走表 200 → eno2 → 192.168.10.1 |

按**网段**匹配而非具体 IP,DHCP 换地址也不会失配。验证:

```bash
ip route get 100.64.0.11  from 192.168.10.86   # → utun0
ip route get 192.168.10.1 from 192.168.10.86   # → eno2 table 200
ip route get 8.8.8.8      from 192.168.31.116  # → eno1(未受影响)
```

### 无人值守重启后的恢复(2026-09-22 实测,含一次结论更正)

#### 结论先行

| 通道 | 主机重启后 | 是否需要人工介入 |
| --- | --- | --- |
| SSH(经 Beyond 内网穿透) | 自动恢复 | 不需要 |
| RDP 3390 **端口监听** | 自动恢复 | 不需要 |
| RDP **登录认证是否成功** | **未验证** | 见下文 |

> **更正记录**:本节早先的版本断言"RDP 重启后不会自动恢复,需要远程解锁钥匙环",并给出了一条
> `gnome-keyring-daemon --unlock` 的命令。**两条都是错的**,已在 2026-09-22 的对抗性复核中被推翻并删除。
> 错误原因见下面两小节。

#### RDP 端口监听与钥匙环无关

3390 是否监听,取决于 **GNOME 图形会话(`graphical-session.target`)是否存在**,与登录钥匙环是否解锁无关。
本次开机日志的精确时序:

```
17:15:54.170  gdm-autologin: gkr-pam: couldn't unlock the login keyring.   ← 钥匙环锁着
17:15:58.739  Reached target graphical-session.target
17:15:59.249  gnome-remote-desktop: RDP server started                     ← 钥匙环仍锁着,已在监听
17:16:07      (此时才由本地手工解锁钥匙环)
```

即 grd 在钥匙环**锁定状态下**仍然正常启动并监听。反向实验同样成立 —— 执行 `cli`
(`systemctl isolate multi-user.target`)后:

```
17:53:55.339  Stopped target graphical-session.target
17:53:56.078  gnome-remote-desktop: RDP server stopped
```

**所以:处于 CLI 模式时 3390 必然不监听,这是设计行为,不是故障。** 切回 `gui` 即恢复。
排查 RDP 不通时,第一件事是确认当前是不是 CLI 模式,而不是去查钥匙环。

#### 仍未验证的一点:锁定状态下能否登录成功

端口监听 ≠ 能登录进去。grd 在 RDP 的 NLA 认证阶段要从登录钥匙环读取用户名与密码
(二进制内含 `secret_password_lookup_sync` 以及 "Username not set" / "Password not set" 字样)。
钥匙环锁定时这次读取是直接失败,还是会触发只在本地屏幕上弹出的提示,**目前没有验证过**。

验证方法:在一次真正的无人值守重启之后(不要在本地碰键盘、不要解锁钥匙环),直接从远端尝试
RDP 登录 192.168.31.116:3390。这是唯一能确定答案的实验,尚未做过。

`remote-access-watchdog` 对这种情况是**盲的**:它的 RDP 判据是"服务 active 且 3390 有监听",
"能连上但登不进去"不会被它发现,也不会触发任何动作。

#### 为什么不能用 gnome-keyring-daemon 远程解锁(已证伪)

曾经设想的做法是 SSH 进来后 `printf '%s' "$PW" | gnome-keyring-daemon --unlock`,
让密码交给已在运行的 daemon。**这条路不成立**,线级(wire-level)证据:

| 调用方式 | 实际经控制套接字发出的内容 |
| --- | --- |
| `--unlock`(裸) | **一个字节都没发,甚至没有连接** —— 它直接去 bind 自己的套接字,另起一个互不相干的实例 |
| `--start` | op=0(INITIALIZE),载荷是 components 与环境变量,**不含密码** |
| `--replace` / `--replace --unlock` | 仅 9 字节:凭据字节 + op=3(**QUIT**),**不含密码** |

结论:这个二进制**从不**把密码经控制套接字交给已运行的 daemon。`--replace --unlock` 的语义是
"杀掉旧 daemon,自己起一个新的",不是"原地解锁"。此外 `--start` 与 `--unlock` 互斥
(二进制内有 `The --start option is incompatible with --unlock`)。

当初的误判来自一次不充分的验证:只测了 `--start` 会调用 `discover_other_daemon` 找到已有 daemon,
就外推认为 `--unlock` 走同一条路径。实测表明 `--unlock` **不**走这条路径。

纯 D-Bus 的 `org.freedesktop.Secret.Service.Unlock` 方法也不可用:它的签名是 `ao → (ao, o)`,
必然返回一个 prompt 对象,而 prompt 的实现者是 **gnome-shell**,弹窗画在本地屏幕上,SSH 侧看不到也答不了。
`secret-tool`(libsecret CLI)本机未安装。

#### 为什么 SSH 能全自动恢复

| 组件 | 状态 | 说明 |
| --- | --- | --- |
| `ssh.socket` | enabled + active | Ubuntu 24.04 用 socket 激活。`systemctl is-enabled ssh.service` 返回 `disabled` 是**正常现象**,真正生效的是 `ssh.socket`。 |
| `docker.service` | enabled | |
| `beyondnetwork_edge` | `RestartPolicy=always` | host 网络 + 特权模式,且**无挂载卷** —— 凭据在容器自身文件系统内,重启不丢。 |
| `mihomo.service` | enabled | `ExecStartPre` 检查基础网络和配置;`ExecStartPost` 重建 Beyond 明细路由、重启 edge 容器与 grd。 |

登录方式:`~/.ssh/authorized_keys` 有 3 把公钥,`PubkeyAuthentication` 取默认 `yes`,
`KbdInteractiveAuthentication no`。密码认证亦可用(本次启动日志有 `Accepted password for descfly`)。

已知空窗:`ensure-remote-access.sh` 在 17:17:07 执行时 `utun0` 上还没有 `100.64.0.0/16` 路由,
即 mihomo 链条跑完时 overlay 尚未可用,这段时间远程 SSH 连不进来。补救靠 `remote-access-watchdog`
的 L2 分支。备用入口:`ssh descfly@192.168.31.116`(eno1 网段,同一台机器,sshd 监听 `0.0.0.0:22`)。

#### 重启后可能彻底失联的两个硬风险

**风险一:`/etc/fstab` 三个数据盘都没有 `nofail`。**

```
/data1  ntfs  defaults  pass=0
/data2  ntfs  defaults  pass=0
/data3  ext4  defaults  pass=2
```

三者均 `RequiredBy=local-fs.target`。任一磁盘掉线、UUID 变化,或 `/data3` 开机 fsck 失败,
`local-fs.target` 即失败 → 系统进入 `emergency.target` → **SSH 与 RDP 全部不可用,只能到机器跟前处理**。
本机是双系统,`/data1`、`/data2` 是 ntfs,Windows 若留下脏位或休眠文件会直接触发该路径。

缓解:给三条 fstab 记录加 `nofail`(并考虑 `/data3` 改 `pass=0`),使磁盘故障不再阻断开机。
**在启用 watchdog 的自动重启之前应当先处理这一条** —— 否则一次自动重启可能把机器变成远程够不着的状态。

**风险二:日志持久化尚未真正生效。**

`/var/log/journal` 目录已建但为空,`journalctl --header` 显示当前仍写在 `/run/log/journal`,
`journalctl --list-boots` 只有 IDX 0。也就是说**下一次重启会销毁本次启动的全部日志**,
死机与自动重启的现场依然无从追查。

修复:

```bash
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald
journalctl --header | grep -m1 '/var/log/journal'    # 出现该路径才算生效
```

#### 重启后不会自动回来的东西

- 宿主机与各容器内的 **tmux 会话**。
- 所有 `RestartPolicy=no` 的开发容器(`MLX_chipyard_dev`、`AgentSys_dev`、`GPDPU_dev` 等)。
  若希望它们随主机回来:`docker update --restart unless-stopped <容器名>`。
- 宿主机上监听 127.0.0.1 的 bun 进程(3010/3011/3020/3021/3022,含 DeepSeek 模型网关 3021)——
  它们是用户态进程,没有任何 systemd 单元覆盖,重启后需手动拉起。

### 运行期守护:remote-access-watchdog

一个独立于 mihomo 的开机自启系统服务,周期性检查 Beyond 隧道与 RDP,分级自愈,最后一级才重启主机。

- 脚本:`network/scripts/remote-access-watchdog.sh` → 安装到 `/etc/mihomo/remote-access-watchdog.sh`
- 单元:`network/systemd/remote-access-watchdog.{service,timer}` → `/etc/systemd/system/`
- 安装:`sudo bash network/scripts/install-watchdog.sh`(幂等,可重复执行)

#### 判据:为什么换掉旧的(2026-09-25 重做)

**旧判据被完整骗过 34 小时。** 它只看「edge 与任一节点有 UDP `:3005` ESTAB」。
校园网认证劫持期间 edge 拿不到节点配置、隧道从未建立,但那条 UDP 保活会话一直
ESTAB —— 判据始终满足,watchdog 一次都没报警、更没升级到重启。同期 `utun0` 的
rx/tx 恒为 `0/0`,却被判"隧道正常"。

新判据用**三个独立信号**,共同特点是**都不依赖远端对端是否在线**
(这是旧设计正确的那一半:不能用 `utun0` 的 rx/tx 增长,对端一关机它本来就不动,
会导致每 20 分钟自重启一次、打断实验):

| 信号 | 健康期 | 劫持期(实测) | 说明 |
| --- | --- | --- | --- |
| **① TCP `:30004` ESTAB** | 4 条 | **0 条**(全 SYN-SENT) | edge 与节点的控制通道,旧判据的盲区 |
| **② `edge.log` 的 `[E]` 行数增长** | 不增长 | 每 10 秒 1 条 | 直接症状 `invalid character '<'` |
| ③ `utun0` 存在且有 overlay 路由 | 有 | 有 | 原 L2 检查,保留 |

①②都通过才算健康。② 用**行数增量**而不是解析时间戳 —— 避开时区问题,也不会
因为历史错误(文件里已有的 14 行)误判;首次运行只记基线。

```bash
# 手工核对这两个判据
docker exec beyondnetwork_edge ss -tnap | grep -c 'ESTAB.*:30004'     # 期望 >= 1
docker exec beyondnetwork_edge grep -c '\[E\]' /var/log/edge.log      # 与上次比较,不增长即正常
cat /run/remote-access-watchdog.errcount                               # watchdog 记的基线
```

#### 两个计数器:为什么需要第二个

| 计数器 | 累加条件 | 清零条件 | 驱动 |
| --- | --- | --- | --- |
| `STATE` | 隧道**判据失败** | 判据通过,或 L1/L2 做了动作 | L3 重启 edge 容器 |
| `ANYFAIL` | **任何形式的未确认健康**(容器没跑 / utun0 缺失 / 无 overlay 路由 / 判据失败) | **只在隧道确认健康时** | L4 重启主机 |

只有 `STATE` 时有个洞:L1(容器未运行)和 L2(utun0 异常)两个分支**会清零它**
—— 因为那两级已经做了动作,应当给它重新观察的机会。但副作用是:**若 edge 反复崩到
utun0 消失,每轮都走 L2、每轮清零,L4 永远不会触发**,与"无法恢复时必须重启"直接冲突。

`ANYFAIL` 独立累加、只在确认健康时归零,补掉这个洞。逻辑仿真(阈值 5 轮):

| 失败模式 | 触发 L4 |
| --- | --- |
| A 判据持续失败(校园网劫持型) | 第 5 轮 |
| B 反复抖动(edge 崩 → utun0 消失 → 重启 → 又崩) | 第 5 轮 |
| C 混合(容器/接口/判据交替) | 第 5 轮 |
| D 中途恢复一次 | 第 8 轮(恢复时归零,重新计) |

旧逻辑在 **B / C 下永不触发**。

一个刻意的例外:**容器不存在**(被删了)时不累加 `ANYFAIL` —— 重启主机也变不出
一个被删除的容器,只会造成无意义的反复重启。这种情况只记日志,提示人工重装。

#### 重启保证:三层,从温和到强硬

问题:`systemctl reboot` 可能被卡住的单元拖住(未响应的 `umount`、NFS、容器),
于是"触发了重启"却没真的重启 —— 人不在机器旁就彻底失联。

| 层 | 手段 | 覆盖的故障 | 何时执行 |
| --- | --- | --- | --- |
| 1 | `systemctl reboot` | 系统正常、只是隧道坏了 | 首次达到 L4 |
| 2 | `reboot --force`(直接调 `reboot(2)`,不 umount、绕过 PID 1) | 关机流程被卡住的单元拖住 | 下一轮发现还活着 |
| 3 | `sysrq-b`(完全绕开用户空间) | 连 `reboot --force` 都没反应 | 第 2 层后 10 秒 |
| 4 | 硬件看门狗(`iTCO_wdt`) | **内核卡死**,定时任务根本不被调度 | 可选,见下 |

**为什么不直接 `sudo reboot`** —— `/sbin/reboot` 就是 `/bin/systemctl` 的软链,
`reboot` 与 `systemctl reboot` **完全等价**;而本服务 `Type=oneshot` 且**没有 `User=`,
本就以 root 运行**,加 `sudo` 只会多一层 sudoers 依赖,不增加任何能力。

**升级的触发机制(2026-09-25 改过一次设计)**:在 `/run` 里放一个"已请求优雅重启"
标记。`/run` 是 tmpfs —— **重启成功它自动消失,不需要任何清理逻辑**。若下一轮
(5 分钟后)timer 跑起来发现标记还在,就说明上次没重启成功,直接升级强度。

> 早先的实现用 `systemd-run --on-active=180s` 布置瞬态定时器兜底。**那个设计有缺陷**:
> 瞬态定时器依赖 systemd 本身还能响应,而"优雅重启卡住"最坏的情形正是 PID 1 自己
> 卡住 —— 那时定时器同样不会触发。现在的做法只依赖 timer 还在被调度(能执行到
> 这段代码就证明它在跑),覆盖面更广。

冷却逻辑有个配套修正:`COOLDOWN_SEC` 只拦"新的一次重启";**已请求过优雅重启而机器
仍在时必须放行**去升级强度,否则会卡在 2 小时冷却里永远起不来。

第 3 层覆盖的是前两层都救不了的情况:**内核一旦卡死,watchdog 这个定时任务不会被
调度,`systemctl reboot` 也发不出去**。只有芯片组里的硬件计数器能强制复位。

```bash
sudo bash network/scripts/enable-hardware-watchdog.sh
```

它加载 `iTCO_wdt`(Supermicro X12DAi-N6 的 Intel 芯片组看门狗)、写
`/etc/modules-load.d/watchdog.conf` 使其开机自载、并把 `RuntimeWatchdogSec=60`
交给 systemd 喂狗。

**要权衡再决定**:系统只是"很慢"(极重 IO、内存压力)而没真卡死时,也可能被硬件
复位;而硬件复位是断电级的、不做 `sync`,未落盘数据会丢。跑长实验的机器上,
一次误复位会打断实验。**不接受这个风险就不要启用**——前两层已覆盖绝大多数情况。

#### 给数据盘加 nofail(自动重启的硬前提)

```bash
sudo bash network/scripts/fstab-add-nofail.sh
```

改前的三行:

```
UUID="C0404B9D404B98D4"                    /data1  ntfs  defaults  0 0
UUID="6200513300510F81"                    /data2  ntfs  defaults  0 0
UUID="8738056c-9425-4c92-b898-744ff67fce2f" /data3  ext4  defaults  0 2
```

改后:

```
... /data1  ntfs  defaults,nofail,x-systemd.device-timeout=10s  0 0
... /data2  ntfs  defaults,nofail,x-systemd.device-timeout=10s  0 0
... /data3  ext4  defaults,nofail,x-systemd.device-timeout=10s  0 2
```

两个选项各管一件事:`nofail` 让挂载失败不再拖垮 `local-fs.target`;
`x-systemd.device-timeout=10s` 让**设备迟迟不出现**时不要一直等下去(默认 90 秒)。

**保留 `defaults` 是刻意的** —— 它与 `nofail` 不冲突,去掉反而会改变
`rw/suid/dev/exec/auto/nouser/async` 这些默认值。

脚本的安全措施:改前备份到 `/etc/fstab.bak.nofail-<时间戳>`;改后跑
`findmnt --verify`,**不通过立即自动回滚**;然后 `systemctl daemon-reload`
重新生成 `.mount` 单元。**只改挂载选项,不动任何已挂载的文件系统,无需重启。**
幂等,重复执行会逐行报"已有 nofail,跳过"。

回滚:`sudo cp -a /etc/fstab.bak.nofail-<时间戳> /etc/fstab && sudo systemctl daemon-reload`

关于 `/data3` 的 `pass=2`:把它改成 `0` 能跳过开机 fsck,但那会让文件系统错误长期
积累不被发现。**更好的做法是保留 fsck、靠 `nofail` 兜住失败后果** —— 脚本因此不动
这一列。

#### 人不在机器旁时,重启到底能不能恢复

能,前提是故障属于"重启可解"的那一类。开机链会自己做完这些:

```
mihomo.service
 ├─ ExecStartPre  ① ensure-campus-net.sh      确认基础网络
 ├─ ExecStartPre  ② ensure-config.sh          配置自检 + 快照健康门禁
 ├─ ExecStart        verge-mihomo              TUN + 通用分流
 ├─ ExecStartPost ③ ensure-beyond-underlay.sh 装 /32 → beyond.conf 指定的网卡
 └─ ExecStartPost ④ ensure-remote-access.sh   重启 edge 容器 + RDP
```

外加 `ssh.socket` 开机自启、`beyondnetwork_edge` 是 `RestartPolicy=always`。

**重启救不了的两类,要认清**:

| 故障 | 为什么重启无用 |
| --- | --- |
| 上游链路本身坏了(如校园网认证掉) | 2026-09-25 实测:重启后依然离线。这类只能换链路或恢复认证 |
| 磁盘挂载失败 | `/etc/fstab` 的 `/data1` `/data2` `/data3` 均为 `defaults`、**缺 `nofail`**,任一盘故障或 `/data3`(`pass=2`)fsck 失败 → `emergency.target` → **SSH 与 RDP 全不可用,只能到机器跟前** |

第二条直接决定"自动重启"是救援还是变砖。**它是这套恢复机制唯一的硬前提** ——
在依赖 L4 自动重启之前应当先给那三行加 `nofail`。

#### 节奏

| 参数 | 值 | 含义 |
| --- | --- | --- |
| `OnBootSec` | 10min | 开机后等 10 分钟才首次检查,给 mihomo 启动链(`TimeoutStartSec=240`)和 edge 重连留足时间,避免开机瞬间误判 |
| `OnUnitActiveSec` | 5min | 此后每 5 分钟检查一次 |
| `IgnoreOnIsolate` | true | `cli` / `gui` 模式切换(`systemctl isolate`)不会把它踩掉 |

#### 判据:为什么用底层 UDP 会话而不是 utun0 收发计数

判断隧道是否建立,用的是「edge 进程与任一 Beyond 节点之间存在底层 UDP `ESTAB` 会话」。

不能用 utun0 的收发计数,因为**对端(你的 Mac)不在线时计数本来就不动**。拿它当判据会导致 Mac 一关机,主机就每 20 分钟自己重启一次,打断 tmux 里正在跑的实验。

节点清单来自 `/run/beyond-underlay.routes`(由 `ensure-beyond-underlay.sh` 在 mihomo 的 `ExecStartPost` 阶段写入;旧路径 `/run/beyond-eno2.routes` 仍兼容)。`/run` 是 tmpfs,重启即清空,因此脚本内置了节点 IP 前缀作为兜底,不会因为该文件尚未生成而误判。

#### 分级升压

| 级别 | 触发条件 | 动作 | 是否影响连续计数 |
| --- | --- | --- | --- |
| L1 | 容器不在 `running` | `docker start` | 计数清零 |
| L2 | `utun0` 缺失,或无 overlay 路由 | `docker restart edge` | 计数清零 |
| L3 | 容器 running、utun0 正常,但无底层 UDP 会话 | `docker restart edge` | 计数累加 |
| L4 | 同上且连续 5 轮 | `systemctl reboot` | —— |
| RDP | `gnome-remote-desktop` 不是 active,或 3390 无监听 | 重启该用户服务 | **与隧道计数无关** |

**重启主机的完整时间线**(首次发现异常记为 0 分钟):

```
第1轮  0 分钟  → 重启 edge 容器(第 1 次尝试)
第2轮  5 分钟  → 重启 edge 容器(第 2 次尝试)
第3轮 10 分钟  → 重启 edge 容器(第 3 次尝试)
第4轮 15 分钟  → 重启 edge 容器(第 4 次尝试)
第5轮 20 分钟  → 重启主机
```

即:**只有 Beyond 隧道异常、且连续 20 分钟内 4 次容器重启全部无效,才会重启主机。**

#### 不会触发重启的情况

- RDP 异常**永远不会**导致重启主机。脚本中 `do_reboot` 只有一个调用点,位于隧道分支内;RDP 检查段落没有任何重启主机的路径。
- 容器不存在(被删除)→ 只记日志,提示人工重装,不重启。
- 容器反复退出 → 每轮 `docker start`,计数被清零,永远升不到 L4。
- `utun0` 反复缺失或丢路由 → 每轮 `docker restart`,计数被清零,永远升不到 L4。

最后三条是有意的取舍:只要 L1/L2 还能"做点什么",就不升级到重启主机。好处是容器侧的反复抖动不会误触发重启;代价是这类故障可能永远到不了 L4,需要人工介入。

任何一轮检测到底层会话恢复,连续计数立即归零。

#### 两道额外的保险

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `MIN_UPTIME` | 900 秒 | 开机不足 15 分钟一律不重启,防止引导循环 |
| `COOLDOWN_SEC` | 7200 秒 | 两次自动重启至少间隔 2 小时。时间戳写在 `/var/lib/remote-access-watchdog.reboot`,该路径在磁盘上,跨重启保留 |

#### 自动重启会丢什么

- 宿主机与各容器内的 **tmux 会话**全部丢失。
- `RestartPolicy=no` 的容器不会自动起来(当前为 `MLX_chipyard_dev`、`AgentSys_dev`、`GPDPU_dev`)。若希望它们随主机回来,执行 `docker update --restart unless-stopped <容器名>`。
- `beyondnetwork_edge` 是 `always`,会自动回来。

#### 已知的行为边界

如果 Beyond 云端长期不可用(故障不在本机),watchdog 会每 2 小时重启一次主机,且不会自行停止。目前没有"连续 N 次重启无效即放弃"的上限。若需要该上限,应在 `do_reboot` 中增加对连续自动重启次数的统计。

#### 查看运行情况

```bash
systemctl list-timers remote-access-watchdog.timer      # 下次触发时间
journalctl -u remote-access-watchdog -f                  # 实时日志
journalctl -t remote-access-watchdog --since today       # 自动重启记录(logger 打的标签)
cat /run/remote-access-watchdog.state                    # 当前连续失败轮数(0 表示正常)
cat /var/lib/remote-access-watchdog.reboot               # 上次自动重启的 Unix 时间戳
```

#### 日志持久化(安装脚本一并开启)

默认 journald 只把日志放在内存里,重启后上一次启动的日志全部丢失 —— 这会让死机排查无从下手。安装脚本会创建 `/var/log/journal`、设置 `Storage=persistent` 与 `SystemMaxUse=500M`。开启后可用 `journalctl -b -1` 查看上一次启动的日志。


### 命令在哪一层执行

```
Mac ──SSH/RDP──▶ 宿主机 shell ──dtm/dsh──▶ 容器 shell ──▶ 容器内 tmux
                      │                         │
                 d* 命令在这层             tmux 命令在这层
```

| 层 | 可用命令 | 不可用 |
|---|---|---|
| **宿主机**(本地终端 / SSH / RDP 内终端) | `cli` `gui` `guistat`、`netreset` `netstat-paper`、`dls` `dsh` `dtm` `dtl`、`docker` | 容器内的 `tmux`(不是同一个进程空间) |
| **容器内** | `tmux`、项目工具链(claude / python / verilator …) | `d*` 命令、`docker`(未做 docker-in-docker) |

`dtm` 一步跨层:`docker exec -it <容器> tmux new-session -A -s work`。

### 什么能活过什么

| 事件 | GUI 程序 | RDP(3390) | 宿主机 SSH 会话 | 容器 | 容器内 tmux 会话 |
|---|---|---|---|---|---|
| SSH 断线 | ✅ | ✅ | ❌ **死**(除非在 tmux 里) | ✅ | ✅ |
| RDP 断开 | ✅ | — | ✅ | ✅ | ✅ |
| `cli`(isolate) | ❌ 死 | ❌ 死 | ✅ | ✅ | ✅ |
| **重启** | ❌ | ❌ | ❌ | ⚠️ `RestartPolicy=no` 的**不会自动回来** | ✅ overlay 保留,容器起回来即在 |
| 容器 `stop`/`start` | — | — | — | ✅ | ✅ tmux 二进制还在,但**会话没了** |
| 容器**重建** | — | — | — | — | ❌ overlay 全丢(`ensure_tmux` 会重装 tmux) |

> **重启后容器不自动恢复**:三个开发容器是 `RestartPolicy=no`。用
> `docker start MLX_chipyard_dev AgentSys_dev GPDPU_dev` 起回来,或改成
> `docker update --restart unless-stopped <容器>` 让它们开机自启。
> `paper-analysis-*` 服务容器已是 `unless-stopped`,重启后自动恢复。

### 操作逻辑

```
① 连接 ──▶ ② 建会话/接回 ──▶ ③ 干活 ──▶ ④ 脱离 ──▶ 换任意入口回到 ②
                                          └──▶ ⑤ 结束会话(活干完了)
```

#### ① 连接:到达宿主机 shell

| 入口 | 怎么进 |
|---|---|
| 本地 GUI | 桌面开 Terminal |
| 本地 CLI | `Ctrl+Alt+F3` → TTY 登录 |
| 远程 GUI | Windows App → `192.168.31.116:3390`(descfly / <RDP密码>)→ 里面开 Terminal |
| 远程 CLI | `ssh descfly@192.168.31.116` |

**四个入口之后,命令完全相同** —— 这就是入口透明。

#### ② 建会话 / 接回(同一条命令)

| 会话在哪 | 建或接 | 列出 | 短暂用(断开即死) |
|---|---|---|---|
| **宿主机** | `tmux new -A -s <名>` | `tmux ls` | 当前 shell 直接敲命令 |
| **容器** | `dtm <容器> [名]` | `dtl <容器>` | `dsh <容器>` |

- `-A` = 有则接回、无则新建 → **建和接是同一条命令**,不用先判断
- `dtm <容器>` 会话名默认 `work`;`dtm <容器> train` 指定名字
- 有哪些容器:`dls`

**会话隔离**:宿主机和每个容器各有独立的 tmux server(socket 分别在
`/tmp/tmux-1000/` 与各容器的 `/tmp/tmux-0/`,`/tmp` 不共享)。
**在哪一层建的,就回哪一层找**,`tmux ls` 只报告当前层。

#### ③④⑤ 会话内操作

| 操作 | 按键 / 命令 | 记法 |
|---|---|---|
| **④ 脱离**(任务继续跑,日常用这个) | `Ctrl+b` 然后 `d` | **d**etach |
| **多开窗口** | `Ctrl+b` 然后 `c` | **c**reate |
| **切换窗口** | `Ctrl+b` 然后 `数字` | 状态栏上看得见编号 |
| 切换(其他方式) | `n` 下一个 / `p` 上一个 / `w` 列表选 | **n**ext / **p**rev / **w**indow |
| 窗口改名 | `Ctrl+b` 然后 `,` | — |
| 关当前窗口 | 敲 `exit` | — |
| **⑤ 结束整个会话** | 关完所有窗口,或 `tmux kill-session -t <名>` | — |

所有快捷键都是**先按 `Ctrl+b` 松开,再按第二个键**。

进会话后屏幕最下方是状态栏,左边即窗口列表,带 `*` 的是当前窗口:

```
0:edit  1:build  2:logs*
```

> **脱离 ≠ 退出**:`Ctrl+b d` 走人,任务继续;敲 `exit` 是关窗口,活就没了。日常只用脱离。

#### 两个场景

**远程**(RDP 看文档 + SSH 跑实验,并行,不切 CLI):

```bash
ssh descfly@192.168.31.116
dtm MLX_chipyard_dev          # 容器里跑实验
python train.py
# Ctrl+b d                     # 脱离
exit                           # 退出 SSH,实验继续跑
```
同时 Windows App 连 `192.168.31.116:3390` 看文档。两条链路独立,互不影响。

**本地**(随时切换):

```bash
dtm MLX_chipyard_dev          # 和远程 SSH 进的是同一个会话
python train.py
# Ctrl+b d

guistat                        # 要显存时
cli                            # 关图形(本终端一并关闭,正常)
#   → Ctrl+Alt+F3 登录 TTY
dtm MLX_chipyard_dev          # 现场原样还在
gui                            # 完事切回图形,在屏幕前登录
```

> **远程不切 CLI 的原因**:`gnome-remote-desktop` 是用户级服务,`cli` 后随图形会话一起消失;
> `gui` 之后 GDM 会自动登录并重建会话(已实测,见下),但远程桌面仍需在本机操作一次才能恢复。
> 能服务登录界面的 3389 需要 TPM,本机(Supermicro X12DAi-N6)没有。
> 代价仅为保留约 1292 MiB 显存(GPU0 的 5%),换零风险。
>
> **实测补充(2026-09-15)**:GDM 自动登录**并非只在开机首次生效** —— 同一天三次会话
> (含两次 `systemctl restart gdm3` 之后的)全部是 `gdm-autologin`,零次 `gdm-password`;
> 钥匙环 `login.keyring` 为 `crypto=00`(无密码),配合 PAM `pam_gnome_keyring.so auto_start`
> 自动解锁;`gnome-remote-desktop` 在会话建立后 **1 秒内**就绪,3390 监听、凭据可读。
>
> 即 GDM 登录、钥匙环、远程桌面自启**三层都已全自动**,但远程切回图形后仍需在本机
> 操作一次才能用上远程桌面 —— 卡点不在这三层。记下来是为了避免以后重复排查自动登录。
>
> 本地 `cli` / `gui` 的 sudo 密码已由 `sudoers/gui-cli-switch` 免除。

#### 存活边界

| 事件 | tmux 会话(主机/容器) | 裸终端里的进程 |
|---|---|---|
| SSH 断线 / 关终端 | ✅ | ❌ |
| RDP 断开 | ✅ | ✅(桌面终端还在) |
| `cli` 切换 | ✅ | ❌ |
| **重启** | ❌ 会话丢;容器还需 `docker start` | ❌ |

**铁律:超过一分钟的活,先进 tmux。唯一活不过的是重启。**
