# 开发环境指南:CLI/GUI 透明 · 容器/宿主透明 · VPN 分流

> 生成于 2026-09-14。适用本机(ubuntu, Supermicro X12DAi-N6, 双 RTX 4090)。

## 为什么用 tmux

**把会话从客户端剥离,只靠 CLI 就能恢复。**

| 出了什么事 | 不用 tmux | 用 tmux |
|---|---|---|
| VS Code 丢失容器连接 / 关掉编辑器 | ❌ 终端连同任务一起没 | ✅ 任务继续跑,`dtm <容器>` 原样接回 |
| SSH 断线、关掉终端窗口 | ❌ 同上 | ✅ 同上 |
| 切到 CLI 模式(`cli`)释放显存 | ❌ 桌面终端里的活全丢 | ✅ 不受影响 |
| 换个入口继续干(本地↔远程) | ❌ 只能重开、从头来 | ✅ 四个入口同一条命令接回 |

**恢复只需要 CLI** —— 不依赖 VS Code、不依赖图形界面。一条 `ssh` 加一条 `dtm` 就回到现场。

**一个例外:容器重启会丢会话。** tmux server 是容器内的进程,`docker restart` 后
`tmux ls` 报 `no server running`。但两样东西还在:

- **tmux 二进制**(overlay 层保留;容器**重建**才会丢,而启动脚本的 `ensure_tmux` 会自动装回)
- **claude 对话记录**(`~/.claude` 是宿主机 bind mount)→ 重启后 `dtm <容器>` 新建会话,
  `claude -c` 即可接续对话

所以边界是:**tmux 保护你不受"客户端消失"的影响,但保护不了"容器/主机重启"。**
长实验若怕重启,结果要落盘到挂载目录。

#### 一句话边界

**只要容器和主机不停机、你自己不 exit,tmux 会话就一直在。**

会话消失只有三种原因:

| 原因 | 说明 | 还剩什么 |
|---|---|---|
| **你自己关掉** | 窗口里敲 `exit` 把所有窗口关完,或 `tmux kill-session -t <名>` | — |
| **容器停止 / 重启** | tmux server 是容器内的进程 | tmux 二进制(overlay)、`~/.claude` 对话记录 |
| **主机重启** | 所有进程终止,`/tmp` 开机清空,socket 一并没了 | 磁盘上的一切 |

除此之外——**关编辑器、断 SSH、拔网线、RDP 掉线、`cli` 切换、换入口**——会话统统还在。

所以日常只要守住一条:**走人按 `Ctrl+b d`,不要敲 `exit`。**

## 一句话原则

- **`d*` 命令(宿主机)** = 从外面**进入**容器终端
- **`tmux` 命令(容器内)** = 在里面**分身 / 脱离 / 接回**会话
- 要"回来"的活用 `dtm`,不打算回来的用 `dsh`

## 一、终端工作流:CLI/GUI 透明,容器/宿主透明

### 命令归属:哪边有什么

| 命令 | 宿主机 | 容器内 | 说明 |
|---|:---:|:---:|---|
| `dls` `dsh` `dtm` `dtl` | ✅ | ❌ | 定义在宿主机 `~/.bashrc`,容器内刻意不定义 |
| `docker` | ✅ | ❌ | 容器没做 docker-in-docker |
| `tmux` | ❌ | ✅ | 三个开发容器均已安装 |
| `cli` `gui` `guistat` | ✅ | ❌ | 图形/CLI 模式切换 |

容器内没有 `d*` 命令是**故意的**:它们本质是 `docker exec` 的封装,人已经在容器里就不需要再"进去"一次。

---

### 宿主机命令

```bash
dls                      # 列出开发容器(自动过滤服务容器)
dtm <容器>               # 进容器 + 接上 tmux(会话名默认 work)。有则接回,无则新建
dtm <容器> <会话名>      # 指定会话名,不同任务分开
dtl <容器>               # 看该容器里有哪些 tmux 会话
dsh <容器>               # 只要一个临时 shell(退出即终止其中进程)
```

`dtm` 一步跨过边界,等价于:
```bash
docker exec -it <容器> tmux new-session -A -s work
```
所以用 `dtm` 进去后**不需要**再敲 tmux。

---

### 容器内命令(tmux 原生)

| 宿主机 | 容器内等价 |
|---|---|
| `dtm <容器>` | `tmux new-session -A -s work` |
| `dtm <容器> train` | `tmux new-session -A -s train` |
| `dtl <容器>` | `tmux ls` |
| — | `tmux attach -t <会话名>` |

#### 必记的三个快捷键

| 按键 | 作用 |
|---|---|
| `Ctrl+b` 然后 `d` | **脱离**,回宿主机,容器内进程继续跑 |
| `Ctrl+b` 然后 `c` | 新建窗口 |
| `Ctrl+b` 然后 `n` / `p` | 下一个 / 上一个窗口 |

---

### dsh 与 dtm 的区别

| | `dsh` | `dtm` |
|---|---|---|
| 实质 | `docker exec -it <c> bash -l` | `docker exec -it <c> tmux new-session -A -s work` |
| 断开后进程 | **随终端死**(SIGHUP) | **继续运行** |
| 能否接回界面 | ❌ | ✅ 原样回到现场 |
| 多处同时查看 | ❌ | ✅ VS Code 与 SSH 可同时 attach |
| 适合 | 几秒钟的事 | claude 会话、训练、编译 |

**`dsh` 仍有三个不可替代的场景:**
1. 要把输出留在自己终端的 scrollback 里(tmux 会接管屏幕,detach 后输出就看不到了)
2. 管道 / 重定向到宿主机:`docker exec <c> cat /workspace/out.log > ~/out.log`
3. 一次性维护动作(装包等),避免塞进 `work` 会话和 claude 混在一起

### 典型场景

#### 场景 1:随手看一眼
```bash
dsh AgentSys_dev
nvidia-smi
exit
```

#### 场景 2:跑 claude 长会话(推荐默认做法)
```bash
dtm AgentSys_dev         # 进 tmux
claude                   # 干活
# Ctrl+b 然后 d          # 脱离,claude 继续跑
# 此时可以关 SSH、关 VS Code、甚至切 CLI 模式

```

#### 场景 3:接管 VS Code 终端里已有的 claude
VS Code 集成终端属于客户端,CLI 下接不回。改用 tmux 重开:
```bash
dsh MLX_chipyard_dev
pkill -f claude          # 清掉旧进程,避免同会话两个进程
exit
dtm MLX_chipyard_dev     # 改用 tmux
claude -c                # ~/.claude 宿主机与容器共享,对话接得上
# Ctrl+b d 脱离
```

#### 场景 4:多任务分会话
```bash
dtm MLX_chipyard_dev train      # 训练
python train.py                 # Ctrl+b d
dtm MLX_chipyard_dev logs       # 看日志
tail -f out.log                 # Ctrl+b d
dtl MLX_chipyard_dev            # 查看:train / logs 两个会话
```

#### 场景 5:配合 CLI / GUI 切换
```bash
dtm AgentSys_dev && claude      # 把活放进 tmux,Ctrl+b d 脱离
cli                             # 切 CLI,释放约 1.3 GB 显存
dtm AgentSys_dev                # CLI 下照常接回
gui                             # 需要图形时再切回
```

### GUI / CLI 模式切换

```bash
guistat        # 当前模式 + 两卡显存 + mihomo 状态
cli            # 退到 CLI,释放显存(有确认提示)
gui            # 切回图形
cli-default    # 永久默认 CLI(重启后生效)
gui-default    # 永久默认图形
```

⚠️ `cli` 会杀掉图形会话,**先 SSH 进来再执行**(在桌面终端里跑会把自己也杀掉)。

| 切 CLI 时 | 状态 |
|---|---|
| Docker 容器(含其中的 claude / tmux) | ✅ 保留 |
| SSH | ✅ 保留 |
| mihomo(systemd 常驻) | ✅ 保留 |
| VS Code Dev Containers server(在容器内) | ✅ 保留 |
| gdm / Xorg / gnome-shell / 桌面程序 | ❌ 终止 |
| 桌面共享 3390 | ❌ 终止 |

原因:容器进程位于 `/system.slice/docker-<id>.scope`,`docker.service` 归属 `multi-user.target`,不在 `graphical.target` 的停止范围内。

---

### 为什么容器会话不会被杀

1. `docker.service` / `containerd.service` 的归属是 `WantedBy=multi-user.target` → `systemctl isolate multi-user.target` 时**在保留名单里**
2. `gdm.service` 的归属是 `WantedBy=graphical.target` → 只有它这类被停
3. 容器内的 vscode-server、终端、claude 的 cgroup 全是 `/system.slice/docker-<id>.scope`,由 Docker 守护进程托管,**不在图形会话进程树里**
4. `~/.claude` 是宿主机 ↔ 容器的双向 bind mount → 会话记录同源,`claude -c` / `claude --resume` 两边都能接续

**唯一会毁掉容器内一切的操作**:VS Code 的 *Rebuild Container* / *Reopen in Container*(触发容器重建)。普通的 *Attach to Running Container* 不会。

## 二、VPN 分流:网络栈启动链与人工重置

### 启动链(开机自动,顺序固定)

```
mihomo.service(唯一开机自启入口)
 ├─ ExecStartPre  ① ensure-openvpn3.sh       确保 VPN 会话(无 TUN 环境下握手)
 ├─ ExecStartPre  ② ensure-config.sh         配置自愈:剔除悬空引用 → 回滚 known-good
 ├─ ExecStart     ③ verge-mihomo             内核 + TUN + 全局分流
 ├─ ExecStartPost ④ start claude-vpn-guard   路由守护(收窄/兜底/自愈)
 ├─ ExecStartPost ⑤ ensure-beyond-eno2.sh    给 Beyond 节点装 /32 路由 → eno2(绕开 TUN)
 └─ ExecStartPost ⑥ ensure-remote-access.sh  重启 Beyond 隧道 + RDP
```

- **为什么这个顺序**:mihomo 的 TUN(`auto-route`)接管全局路由后,会按规则把 Claude
  流量分发进 openvpn3 隧道。若 mihomo 起来时隧道不存在,分流规则会指向不存在的接口。
- `ExecStartPre=/etc/mihomo/ensure-openvpn3.sh` 会:已有 198.18.x 隧道则直接放行;
  否则**先断开所有残留会话**(并存多个会话是 tun 编号乱跳、guard 反复误判的根因),
  再用 `/home/descfly/Desktop/waimaot-liuzhixiang.ovpn` 起一个新会话,最多等 45 秒。
- VPN 拉不起来时**只告警不阻断** mihomo,避免彻底断网(guard 会进兜底态保证连通)。
- **② 配置自愈**:订阅刷新可能产出坏配置(见 Bug 4),此步让**重启本身就能修复** ——
  能解析就放行并存 known-good 快照;不能就剔除悬空引用;仍不能就回滚快照。
- **⑤ Beyond 出口**:给 Beyond 节点装主表 `/32 + onlink` 路由指向 eno2,使其**不进 Mihomo TUN**。
  必须排在 ⑥ 之前 —— 路由要先铺好,edge 重启后才会在正确路径上建立会话。详见「Beyond 底层出口」一节。
- **⑥ 隧道与 RDP**:分流路由一变,Beyond 的底层 UDP 会话会僵死、RDP 既有连接会断,
  所以在路由就位后重启这两项。**有健康门槛**(API 9097 可达 + `Mihomo` TUN 存在,
  最多等 25 秒),否则 crash loop 中会每 3 秒重启一次隧道容器。此步**不依赖 guard**。
- `TimeoutStartSec=240`,覆盖 ①⑥ 两步的等待。
- `claude-vpn-guard.timer` **已取消开机自启**,只由 mihomo 拉起;停止 mihomo 时一并停掉,
  否则它会把全部流量兜底进 openvpn3。

### 分流策略的核心(三条原理)

#### 原理 1:路由表优先,mihomo 截取全部流量

mihomo 的 `tun.auto-route: true` 建立 `Mihomo` 虚拟网卡,并装入策略路由:

```
9001: from all to 28.0.0.0/30 lookup 2022
9002: from all lookup 2022 suppress_prefixlength 0
9003: not from all dport 53 lookup main suppress_prefixlength 0
9004: not from all iif lo lookup 2022          # table 2022: default dev Mihomo
```

**这才是"截流"的机制** —— 网络层强制捕获,程序无从选择。
`mixed-port: 7897` 的系统代理是**并行的另一个入口**,只对认 `HTTP_PROXY` 的程序生效,
两者没有优先级关系。(这也是过去只开系统代理时 openvpn3 能正常握手的原因:
它发原始 UDP,不认代理变量,没有 TUN 就不会被拦。)

#### 原理 2:TUN 层没有域名,fake-ip 让域名"以 IP 的身份"参与 rule

**问题的根源:TUN 工作在三层,它收到的是 IP 包 —— 那一层不存在"域名"这个字段。**

而分流规则里大量是域名规则(`DOMAIN-SUFFIX,anthropic.com,OpenVPN-tun0`、
`DOMAIN-SUFFIX,<VPN域名>,DIRECT` …)。域名只在 DNS 阶段出现过,流量进 TUN 时
只剩「目标 IP + 端口」,域名信息已经丢失 —— **域名规则将无从匹配**。

**fake-ip 就是为此而生:给每个域名发一个唯一的 IP 当作它的"代号",
让域名得以用 IP 的形式进入三层,从而参与 rule 匹配。**

```
① DNS 阶段   程序问 <VPN域名> → mihomo 截下(dns-hijack any:53)
             返回代号 28.0.0.4,并记账:28.0.0.4 ←→ <VPN域名>
② 三层       程序往 28.0.0.4 发包 → 进 Mihomo TUN
③ 反查       mihomo 按 28.0.0.4 查出 <VPN域名>   ← 域名回来了
④ 匹配       DOMAIN-SUFFIX,<VPN域名>,DIRECT 得以生效
```

没有 fake-ip,第 ③ 步拿不到域名,第 ④ 步的域名规则形同虚设,
所有流量只能靠 `IP-CIDR` / `GEOIP` 这类三层规则粗粒度分流。

**代号机制附带的三个好处:**

| 好处 | 说明 |
|---|---|
| 把**域名**而非 IP 交给代理 | mihomo 全程持有域名,由代理在它自己的位置解析,拿到正确的 CDN 节点;`redir-host` 用**本地**解析出的 IP,代理连过去常绕路甚至连不上 |
| 域名识别 1:1 精确 | `redir-host` 靠 IP 反查域名,一个 CDN IP 后挂几十个域名,反查有歧义;代号是唯一映射 |
| 不等上游 DNS | 要走代理的域名立即返回代号,省一次真实解析往返,也避免本地 DNS 被投毒/抢答 |

**代价,也就是 Bug 1 的成因:所有程序拿到的都是代号,不是能真正连通的地址。**
对经代理的流量无所谓(mihomo 会在第 ③ 步还原域名并代为连接),
但 **openvpn3 要靠这个地址自己建隧道** —— 它拿着代号 `28.0.0.4` 发握手 UDP,
包进 TUN 后被当作普通流量送进代理,隧道永远建不起来。
所以必须用 `fake-ip-filter` 把 VPN 域名排除在代号机制之外,让它拿到真实 IP。

> **fake-ip 不是 TUN 的必需品** —— `enhanced-mode` 可选 `redir-host`,TUN 照常工作,
> 只是失去以上三点,并退回"先本地解析再连"的模式。
> **fake-ip 也不能指定下一跳** —— 决定流量去哪的只有 `rules`,
> 代号只负责让域名规则"看得见"。


#### 原理 3:规则约束(此处修正)

| 流量 | 应走 | 说明 |
|---|---|---|
| Claude(进程 + `anthropic.com` 等域名) | **openvpn3** (`OpenVPN-tun0`) | 由 `PROCESS-PATH-REGEX,(?i)claude` 与 `DOMAIN-SUFFIX,anthropic.com` 指向 |
| **VPN 服务器自身**(`<VPN域名>` / openvpn3 进程) | **DIRECT 直连 eno1** | ❗**绝不能走 openvpn3** —— 那是"要建隧道却先要有隧道"的死循环;也不能走 clash 代理 |
| 其余一切(pip / conda / HF / docker …) | clash 代理组 | 由最后一条 `MATCH,Others` 兜底 |

> ⚠️ 修正:原表述"VPN 域名的流量只能走 openvpn3"是反的。
> **VPN 域名是 openvpn3 用来连接自己服务器的底层流量,必须绕开一切隧道直连**,
> 否则永远建立不了会话。

`claude-vpn-guard` 负责维持这个约束的路由侧:

- **收窄态(正常)**:清掉 openvpn3 推送的大批路由,只保留 `table 100` + `oif <tun>` 规则
  → 于是**只有被 clash 显式绑定到 `OpenVPN-tun0` 的流量**才进隧道,其余留给 clash。
  这实现了你说的"openvpn3 只承载 Claude 流量"。
- **兜底态(clash 挂了)**:把 `0.0.0.0/1` + `128.0.0.0/1` 指向隧道,全部流量走 openvpn3 保证不断网。

### 实现一:策略功能(service + cli)

**单一开机自启入口 `mihomo.service`**,顺序不可颠倒:

```
ExecStartPre  = /etc/mihomo/ensure-openvpn3.sh                    # ① 无 TUN 环境下建 VPN 会话
ExecStart     = /usr/bin/verge-mihomo -d /etc/mihomo -f …/config.yaml   # ② 内核 + TUN + 分流
ExecStartPost = systemctl --no-block start claude-vpn-guard.timer # ③ 路由守护
ExecStopPost  = systemctl --no-block stop  claude-vpn-guard.timer
```

**为什么顺序不可颠倒**:TUN 一旦先存在就会吞掉 openvpn3 自身的握手 UDP。
`ExecStartPre` 保证 VPN 在 TUN 出现之前就连好。

**配置侧的放行(`/etc/mihomo/config.yaml`)** —— 两者缺一不可:

```yaml
dns:
  fake-ip-filter:
    - '+.<VPN域名>'          # ① VPN 域名返回真实 IP,不给假 IP
rules:
  - PROCESS-NAME,openvpn3-service-client,DIRECT   # ② 握手流量直连,不进代理
  - PROCESS-NAME,openvpn3,DIRECT
  - PROCESS-NAME,openvpn,DIRECT
  - DOMAIN-SUFFIX,<VPN域名>,DIRECT
  - IP-CIDR,<VPN服务器IP-1>/32,DIRECT,no-resolve
  - IP-CIDR,<VPN服务器IP-2>/32,DIRECT,no-resolve
  # …以下为原有规则:Claude → OpenVPN-tun0,其余 → MATCH,Others
```

只改 DNS 不加规则:流量仍会被 `MATCH,Others` 送进代理。
只加规则不改 DNS:规则虽判 DIRECT,但目标是假 IP,发不出去。

**开机自启单元只有两个**,其余全部 disabled:

| 单元 | 职责 |
|---|---|
| `mihomo.service` | 唯一启动链入口 |
| `mihomo-refresh.timer` | 每日 04:30 刷订阅(只换 `proxies:`,保留规则/分组) |
| ~~`claude-vpn-guard.timer`~~ | disabled,由 mihomo 拉起 |
| ~~`clash-verge-service.service`~~ | disabled,GUI 辅助服务会抢 TUN 和 7897 |

**日常 CLI 命令**:

整链控制命令 `netstack`:

| 命令 | 作用 |
|---|---|
| `netstack status` | 状态速览(无需 root),含「GUI 内核数」与「配置校验」 |
| `sudo netstack stop` | 整链停止并撤销残留(内核/会话/网卡/规则/路由/DNS 缓存) |
| `sudo netstack start` | 整链启动(走完五步) |
| `sudo netstack restart` | stop + start |
| `sudo netstack reset` | 四阶段完整重置(= `net-reset.sh`) |
| `sudo netstack heal` | **只修配置**,不动隧道 |

```bash
netstat-paper      # 状态速览:mihomo/guard/openvpn3/TUN/VPN域名解析/兜底路由
netreset           # 一键重置(见下)
systemctl status mihomo
journalctl -u mihomo -n 30 --no-pager | grep ensure-openvpn3
journalctl -t claude-vpn-guard -n 10 --no-pager
```

### 实现二:人工 CLI 重置与重建

#### ⭐ 一键重置(四阶段:撤销 → 验证裸机 → 重施 → 验证)

```bash
netreset           # = sudo /usr/local/sbin/net-reset.sh
```

> **为什么必须有"撤销"阶段**:`pkill` 掉 mihomo **不会**回收它对内核做的改动。
> 曾出现「杀光所有 mihomo 后 openvpn3 依然连不上」,真凶是
> **systemd-resolved 缓存了 fake-ip**(`<VPN域名> → 28.0.0.4 -- link: Mihomo`),
> openvpn3 拿到缓存里的假 IP,而此时 mihomo 已死,包发出去石沉大海。

**阶段 A — 撤销全部影响**

| 步 | 动作 | 为什么 |
|---|---|---|
| A1 | 停 mihomo / guard / clash-verge-service | — |
| A2 | `pkill` 所有内核进程(verge-mihomo/mihomo/clash/clash-meta/clash-verge) | — |
| A3 | 断开**全部** openvpn3 会话 | 并存多会话是 tun 编号乱跳的根因 |
| A4 | 删除残留的 `Mihomo` 虚拟网卡 | 进程死了网卡可能还在 |
| A5 | 清 `ip rule` 9000/9001/9002/9003/9004/9010 与 guard 的 50 | **进程死了不会自动清** |
| A6 | 清空 `table 2022`(mihomo)与 `table 100`(guard) | 同上 |
| A7 | 清兜底路由 `0.0.0.0/1` `128.0.0.0/1` | guard 兜底态遗留 |
| A8 | 清指向已消失接口的 detached 规则 | — |
| A9 | **`resolvectl flush-caches`** | ⭐ 清掉 fake-ip 缓存,否则前面全白做 |

**阶段 B — 验证裸机状态**(任一项不过就停在这里,便于排查)

- VPN 域名必须解析为**真实 IP**(仍是 `28.x` 说明缓存没清干净)
- 无 `90xx` 策略规则残留、`table 2022` 为空
- 直连公网可达(不通 → 物理网络问题,与 VPN 栈无关)

**阶段 C — 重新施加**

`systemctl start mihomo` → `ExecStartPre` 在无 TUN 环境建 VPN 会话 → 内核启动并
**自行重新装上** 9000-9010 规则与 table 2022 → `ExecStartPost` 拉起 guard,
guard 重建 table 100 与收窄规则。

**阶段 D — 验证**

一次打印:会话数(应 1)、tun 地址、Mihomo TUN、mihomo/guard 状态、
策略规则条数、兜底路由条数(应 0)、VPN 域名解析、直连与经 clash 的连通性。

### 已知 Bug 记录(2026-09-14 定位并修复)

#### Bug 1:fake-ip 吞掉 openvpn3 的握手流量

| 项 | 内容 |
|---|---|
| **现象** | openvpn3 会话起不来或反复重连;guard 报「隧道断开,找不到 198.18.x 接口」 |
| **根因** | fake-ip 把 `<VPN域名>` 解析成 `28.0.0.x`,openvpn3 往假 IP 发握手 UDP;该包进 TUN 后落到最后一条 `MATCH,Others`,被**送进 clash 代理**而非直连 |
| **为何旧钉子无效** | guard 钉的 `<VPN服务器IP-1>/32 via eno1` 是按"openvpn3 会用真实 IP"设计的,fake-ip 让它永远拿不到真实 IP,钉子落空 |
| **诊断** | `getent hosts <VPN域名>` 返回 `28.0.0.x` 即中招 |
| **修复** | `fake-ip-filter` 加 `+.<VPN域名>` + 前置 6 条 DIRECT 规则(见「实现一」) |
| **备选方案** | 把 `enhanced-mode` 改成 `redir-host` 也能修好(真实 IP 让钉子生效),但会失去 fake-ip 的三项好处,故不采用 |

#### Bug 2:guard 把 mihomo 热重载到了错误的配置文件

| 项 | 内容 |
|---|---|
| **现象** | guard 反复刷「接口改名·已自愈:clash 绑的是 utun0,实际隧道是 tun0」,随后「兜底生效」,mihomo 不断重启 |
| **根因** | 内核迁到 `/etc/mihomo` 后,`claude-vpn-guard.sh` 的 `CLASH_CFG` 仍指向 GUI 的 `clash-verge.yaml`;它读到过期的 `interface-name: utun0`(其实是 Beyond 的接口名),判定"改名"后执行 `PUT /configs {"path": <GUI配置路径>}`,**把 mihomo 切换去加载 GUI 配置** |
| **诊断** | `grep -E '^CLASH_CFG=' /usr/local/sbin/claude-vpn-guard.sh` 指向 GUI 路径即中招 |
| **修复** | `CLASH_DIR=/etc/mihomo`、`CLASH_CFG="$CLASH_DIR/config.yaml"` |
| **归属** | 2026-09-14 迁移 headless 时引入的回归;guard 本身(2026-09-13 22:13 创建)在 GUI 时代是正确的 |

#### Bug 3:杀掉 mihomo 后残留状态导致 openvpn3 仍连不上

| 项 | 内容 |
|---|---|
| **现象** | `pkill` 掉所有 mihomo/clash 进程后,openvpn3 依然建立不了会话 |
| **根因** | 进程死亡不回收内核状态:① **systemd-resolved 仍缓存 fake-ip**(`<VPN域名> → 28.0.0.4 -- link: Mihomo`),openvpn3 拿到假 IP 发包石沉大海;② `ip rule` 9000-9010 与 `table 2022: default dev Mihomo` 仍在;③ guard 的 priority 50 规则与 `table 100` 仍在 |
| **诊断** | `resolvectl query <VPN域名>` 返回 28.0.0.x;`ip rule show \| grep '^90'` 非空 |
| **修复** | `netreset` 的阶段 A(A4-A9)逐项撤销,其中 **A9 `resolvectl flush-caches`** 是关键;阶段 B 强制验证 DNS 已返回真实 IP 才继续 |
| **教训** | "杀进程"≠"恢复原状"。任何手工 kill 之后都应跑一次 `netreset`,而不是直接重启服务 |

#### Bug 4:订阅刷新产出坏配置,mihomo crash loop

| 项 | 内容 |
|---|---|
| **现象** | 某天起 mihomo 反复重启(实际达 212 次),`Mihomo` TUN 不存在、`table 2022` 为空;guard 看不到 TUN 判定 clash 已死 → 装兜底路由 → **全部流量被塞进 openvpn3**;Beyond 隧道底层出口随之突变而僵死,远程连不上 |
| **根因** | `refresh.py` 每日只替换 `proxies:` 段,而 `proxy-groups` 与部分 `rules` 是**按名字引用节点**的。订阅更新后节点下线(本次是 `日本 中继 05/06/07`)→ 引用悬空 → 整份配置解析失败 |
| **为何重启无用** | `verge-mihomo -t` 直接判定解析失败。`systemctl restart` / `netreset` 只重置**运行态**,改不了**配置内容** —— 重启多少次都是同样结果 |
| **诊断** | `verge-mihomo -d /etc/mihomo -f /etc/mihomo/config.yaml -t`;或 `journalctl -u mihomo \| grep "Parse config error"` |
| **修复(三道闸)** | ① `refresh.py` 剔除 `proxy-groups` 与 `rules` 里的悬空引用 ② 写临时文件后 `verge-mihomo -t` 校验 ③ 通过才原子替换并存 known-good 快照;不通过保留旧配置 |
| **启动自愈** | 新增 `ExecStartPre=/etc/mihomo/ensure-config.sh`:配置能解析→放行并存快照 / 剔除悬空引用后能解析→就地修复 / 仍不行→回滚 known-good。**「重启」本身因此能修复坏配置** |
| **对照实验** | 随机删 5 个订阅节点复现:旧版 `test failed`(会 crash loop),新版剔除 7 处引用后 `test is successful` |

**遗留限制**(不影响启动):分组被剔空后填 `DIRECT`(该组流量改走直连,日志会提示);
回滚到 known-good 时节点可能已过期(能跑 > 起不来);刷新失败是静默的,只记在
`journalctl -u mihomo-refresh`。

#### Bug 5:Clash Verge GUI 抢占 Mihomo TUN

| 项 | 内容 |
|---|---|
| **现象** | systemd 的 mihomo 明明 `active`,但 `Mihomo` 接口时有时无;guard 在「已恢复正常」与「兜底生效」之间反复跳 |
| **根因** | GUI 应用被打开后会**拉起自己的内核**(`-d ~/.local/share/io.github.clash-verge-rev...`),与 systemd 的内核抢同一个 `Mihomo` 设备与 7897 端口。日志时序:`16:45:01 systemd 内核建好 TUN → GUI 内核起来把它销毁 → 16:45:24 guard 判定 clash 未运行` |
| **要点** | 只杀 GUI 拉起的内核没用 —— **GUI 应用是它的父进程,会立刻重生**,必须退出 GUI 应用本身 |
| **诊断** | `pgrep -af verge-mihomo`,出现 `-d /home/...` 的即为 GUI 内核;`netstack status` 的「GUI 内核」一行应为 0 |
| **修复** | 退出 Clash Verge 应用(非仅关内核);`netstack stop` 已包含 `pkill -f clash-verge` |

#### 原始设计的盲区

`claude-vpn-guard`(2026-09-13)只设计了「Claude 流量怎么**进**隧道」,
没有设计「**openvpn3 自己的握手流量怎么出去**」—— 这正是 Bug 1 的根源。
现已由 `ExecStartPre` 的顺序保证 + 配置放行规则双重覆盖。

### 最后手段:基于 Clash GUI 的人工重置与重建

> 仅当 `netreset` 与「分步人工重建」都失效时使用。
> 思路:**先把机器退回一个完全没有任何隧道/代理的干净状态**,
> 再用 GUI 的系统代理(不开 TUN)保住基本连通,然后建 VPN,最后交给 Claude 诊断。

#### 第 1 步:杀死所有可能的 VPN / 代理

```bash
# ① 停掉所有相关 systemd 服务
sudo systemctl stop mihomo.service claude-vpn-guard.timer claude-vpn-guard.service
sudo systemctl stop clash-verge-service.service 2>/dev/null
sudo systemctl stop openvpn.service 2>/dev/null
sudo systemctl stop 'openvpn-client@*' 'openvpn@*' 2>/dev/null

# ② 杀掉所有可能的内核 / 客户端进程
sudo pkill -x verge-mihomo
sudo pkill -x mihomo
sudo pkill -x clash
sudo pkill -x clash-meta
sudo pkill -f clash-verge
sudo pkill -x openvpn

# ③ 断开全部 openvpn3 会话(逐个 Path,直到列表为空)
openvpn3 sessions-list
for sp in $(openvpn3 sessions-list 2>/dev/null | awk '/^ *Path:/{print $2}'); do
    openvpn3 session-manage --session-path "$sp" --disconnect
done
openvpn3 sessions-list          # 应为空

# ④ 确认虚拟网卡都消失(utun0 是 Beyond 隧道,保留不动)
ip -br link | grep -E 'tun|Mihomo'
```

#### 第 2 步:清理残留的路由与策略规则

```bash
# ① guard 的兜底路由
sudo ip route del 0.0.0.0/1   2>/dev/null
sudo ip route del 128.0.0.0/1 2>/dev/null

# ② mihomo auto-route 装的策略规则(优先级 9000-9010)
for pri in 9000 9001 9002 9003 9004 9010; do
    while sudo ip rule del priority $pri 2>/dev/null; do :; done
done

# ③ guard 的 table 100 与 oif 规则
while sudo ip rule del priority 50 2>/dev/null; do :; done
sudo ip route flush table 100  2>/dev/null
sudo ip route flush table 2022 2>/dev/null

# ④ 指向已消失接口的残留规则
ip rule show | grep detached            # 逐条 sudo ip rule del ...

# ⑤ 确认干净:只剩 0/32766/32767 三条默认规则 + eno2 的 199/200
ip rule show
ip route show
```

#### 第 3 步:验证"裸机"状态下网络正常

```bash
getent hosts <VPN域名>    # 应返回真实 IP(没有 mihomo 劫持 DNS 了)
ping -c 3 192.168.31.1
```

### Beyond 底层出口:必须绕开 mihomo TUN(2026-09-20 定位)

**这是本机最容易搞错的一处,先把结论说清楚:**

> Beyond 的底层流量必须**在路由层**就从 eno2 直出,**不能进 Mihomo TUN**。
> 让它「进 TUN 之后再从 eno2 出站」是无效的 —— 两者机制不同,结果也不同。

#### 为什么

NAT 穿透要求 edge 的 UDP **源端口映射稳定**。若流量进了 Mihomo TUN,
mihomo 会**终结这条 UDP 再以自己的端口重新发起**:

- 出站正常 → edge 能注册、能收到 Beyond 的保活包
- 入站打洞失败 → 对端按 Beyond 记录的地址打过来,打到的是 mihomo 的临时映射
- 表现:`utun0` 有少量 `rx`(保活),**`tx` 恒为 0**,远端怎么都连不上

#### 正确做法:主表 `/32` 明细路由 + `onlink`

mihomo 的规则链是:

```
9002: lookup 2022 suppress_prefixlength 0   → 表 2022 只有 default dev Mihomo,被 suppress 跳过
9003: lookup main suppress_prefixlength 0   → 查主表的【明细】路由  ← 在这里拦截
```

所以在**主表**给 Beyond 节点装 `/32` 路由,规则 9003 就会命中它,流量**根本不进 TUN**:

```bash
ip route replace <节点IP>/32 via 192.168.10.1 dev eno2 onlink
```

由 `/etc/mihomo/ensure-beyond-eno2.sh` 自动完成,已接入启动链(见「启动链」一节第 ⑤ 步)。

#### 两个必须处理的坑

| 坑 | 症状 | 处理 |
|---|---|---|
| **网关在主表里不可达** | `ip route replace ... via 192.168.10.1 dev eno2` 报错,一条都装不上 | eno2 的直连路由 `192.168.10.0/24` 被 NetworkManager 放进了**表 200**(见「回包路径」一节),主表没有,内核判定网关不可达。路由必须加 **`onlink`** 显式声明网关在同一链路 |
| **DNS 解析拿到 fake-ip** | 脚本解析出 `28.0.0.x` 并据此装路由,完全无效 | `dig @223.5.5.5` 仍会被 mihomo 的 `dns-hijack any:53` 截走。必须**绑定 eno2 源地址查询**:`dig -b 192.168.10.86 @223.5.5.5 …`;脚本另加 `grep -v '^28\.'` 兜底 |

#### 还要把 Beyond 域名排除出 fake-ip

`/32` 路由只对**真实 IP** 生效。edge 若解析 `api1.beyondnetwork.cn` 得到 fake-ip `28.0.0.x`,
拿着假 IP 去连,路由匹配不上,控制面仍会被 mihomo 中转。所以:

```yaml
dns:
  fake-ip-filter:
    - '+.beyondnetwork.cn'
    - '+.beyondtunnel.com'
    - '+.ipw.cn'          # edge 的 IPv6 探测域名,否则日志刷 dns resolve failed
```

与当初修 openvpn3 握手(`+.<VPN域名>`)是同一手法,原理见「原理 2」。

#### 验证成功的标志

```bash
# ① 四条路由都指向 eno2,而非 dev Mihomo
for ip in <节点IP列表>; do ip route get $ip | head -1; done
#   期望: <ip> via 192.168.10.1 dev eno2 src 192.168.10.86

# ② edge 的 UDP 会话源地址是 192.168.10.86,不是 28.0.0.1
docker exec beyondnetwork_edge ss -unap | grep edge
#   期望: ESTAB 192.168.10.86:xxxxx → <节点IP>:3005 users:(("edge",...))

# ③ mihomo 日志里不再出现 (edge) 的流量
journalctl -u mihomo --since -2min | grep -c "(edge)"
#   期望: 0(控制面与数据面都已绕开)

# ④ utun0 的 tx 开始增长(有真实对端流量,而非只有保活)
```

#### 已证伪的两种做法(勿再尝试)

| 做法 | 为什么无效 |
|---|---|
| mihomo 规则指向 `type: direct` + `interface-name: eno2` 的伪出口 | **仍先进 TUN**(源变成 `28.0.0.1`),只是出站那一跳绑了 eno2,NAT 映射依旧不稳定 |
| 只用 `tun.route-exclude-address` 排除节点 | 方向对,但排除后走**主表默认路由(eno1)**,没解决"从哪块网卡出"。`/32 + onlink` 一步同时解决两件事 |

脚本留在 `network/scripts/deprecated/` 仅作记录。


### 回包路径:非对称路由(最隐蔽的坑)

**症状**:远端 TCP 握手成功,但 RDP/SSH 认证总是超时。看起来像密码问题,其实是网络。

**根因**:双网卡各有一条 DHCP 默认路由。请求从 `eno2`(192.168.10.86)进来,
回包却按主表默认路由从 `eno1`(192.168.31.x)出去,对端收不到应答。

**修复**(写进 NetworkManager,重启后持久):

```bash
nmcli con mod "<eno2 连接名>" ipv4.route-table 200
nmcli con mod "<eno2 连接名>" ipv4.routing-rules \
  "priority 199 from 192.168.10.0/24 table 254 suppress_prefixlength 0, \
   priority 200 from 192.168.10.0/24 table 200"
nmcli con up "<eno2 连接名>"
```

| 规则 | 作用 |
|---|---|
| `route-table 200` | eno2 的路由(含默认路由)放进独立表,不与 eno1 在主表争 |
| 优先级 **199** | 源自 10.x 的包**先查主表明细路由**(如 `100.64.0.0/16 → utun0`),但忽略主表默认路由 —— 少了这条,回 overlay 对端的包会被错误地送出 eno2 |
| 优先级 **200** | 其余走表 200 → eno2 → 192.168.10.1 |

按**网段**匹配而非具体 IP,DHCP 换地址也不会失配。验证:

```bash
ip route get 100.64.0.11  from 192.168.10.86   # → utun0
ip route get 192.168.10.1 from 192.168.10.86   # → eno2 table 200
ip route get 8.8.8.8      from 192.168.31.116  # → eno1(未受影响)
```

#### ① 连接:到达宿主机 shell

| 入口 | 怎么进 |

#### ② 建会话 / 接回(同一条命令)

| 会话在哪 | 建或接 | 列出 | 短暂用(断开即死) |
|---|---|---|---|
| **宿主机** | `tmux new -A -s <名>` | `tmux ls` | 当前 shell 直接敲命令 |
| **容器** | `dtm <容器> [名]` | `dtl <容器>` | `dsh <容器>` |

- `dtm <容器>` 会话名默认 `work`;`dtm <容器> train` 指定名字
- 有哪些容器:`dls`

**会话隔离**:宿主机和每个容器各有独立的 tmux server(socket 分别在

| 操作 | 按键 / 命令 | 记法 |
|---|---|---|
| **④ 脱离**(任务继续跑,日常用这个) | `Ctrl+b` 然后 `d` | **d**etach |
| **多开窗口** | `Ctrl+b` 然后 `c` | **c**reate |
| **切换窗口** | `Ctrl+b` 然后 `数字` | 状态栏上看得见编号 |
| 切换(其他方式) | `n` 下一个 / `p` 上一个 / `w` 列表选 | **n**ext / **p**rev / **w**indow |
| 窗口改名 | `Ctrl+b` 然后 `,` | — |
| 关当前窗口 | 敲 `exit` | — |
| **⑤ 结束整个会话** | 关完所有窗口,或 `tmux kill-session -t <名>` | — |

```bash
exit                           # 退出 SSH,实验继续跑
```
同时 Windows App 连 `192.168.10.86:3390` 看文档。两条链路独立,互不影响。

**本地**(随时切换):

```bash
dtm MLX_chipyard_dev          # 和远程 SSH 进的是同一个会话
python train.py
# Ctrl+b d

guistat                        # 要显存时
cli                            # 关图形(本终端一并关闭,正常)
#   → Ctrl+Alt+F3 登录 TTY
dtm MLX_chipyard_dev          # 现场原样还在
gui                            # 完事切回图形,在屏幕前登录
```

> **远程不切 CLI 的原因**:`gnome-remote-desktop` 是用户级服务,`cli` 后随图形会话一起消失;
> `gui` 之后 GDM 会自动登录并重建会话(已实测,见下),但远程桌面仍需在本机操作一次才能恢复。
> 能服务登录界面的 3389 需要 TPM,本机(Supermicro X12DAi-N6)没有。
> 代价仅为保留约 1292 MiB 显存(GPU0 的 5%),换零风险。
>
> **实测补充(2026-09-15)**:GDM 自动登录**并非只在开机首次生效** —— 同一天三次会话
> (含两次 `systemctl restart gdm3` 之后的)全部是 `gdm-autologin`,零次 `gdm-password`;
> 钥匙环 `login.keyring` 为 `crypto=00`(无密码),配合 PAM `pam_gnome_keyring.so auto_start`
> 自动解锁;`gnome-remote-desktop` 在会话建立后 **1 秒内**就绪,3390 监听、凭据可读。
>
> 即 GDM 登录、钥匙环、远程桌面自启**三层都已全自动**,但远程切回图形后仍需在本机
> 操作一次才能用上远程桌面 —— 卡点不在这三层。记下来是为了避免以后重复排查自动登录。
>
> 本地 `cli` / `gui` 的 sudo 密码已由 `sudoers/gui-cli-switch` 免除。

#### 存活边界

| 事件 | tmux 会话(主机/容器) | 裸终端里的进程 |
|---|---|---|
| SSH 断线 / 关终端 | ✅ | ❌ |
| RDP 断开 | ✅ | ✅(桌面终端还在) |
| `cli` 切换 | ✅ | ❌ |
| **重启** | ❌ 会话丢;容器还需 `docker start` | ❌ |

**铁律:超过一分钟的活,先进 tmux。唯一活不过的是重启。**
